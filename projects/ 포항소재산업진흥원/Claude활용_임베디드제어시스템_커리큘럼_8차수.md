# Claude 활용 임베디드 제어시스템 개발 — 커리큘럼 (8차수 / 하루 4시간)

- **대상** : 임베디드 개발 실무자 (사내 ESP32 개발 경험자 포함, AI 코딩 도구를 업무에 조금씩 써 본 수준)
- **실습 환경** : 고객사 실제 설비 연동 (사전 환경 조사 필요)
- **최종 산출물** : 센서 → RS-485 → GUI 통합 모니터링 시스템 1식 + 팀 하네스 템플릿

## 설계 축 — 임베디드 실무 × AI 협업 개발

이 과정은 두 축을 겹쳐서 진행합니다. 한 축은 센서에서 RS-485를 거쳐 GUI로 흐르는 데이터, 다른 축은 하네스에서 루프를 거쳐 그래프로 올라가는 AI 협업 개발 성숙도입니다.

### 세 개념 정리 (2026년 현재 통용 기준)

**하네스 엔지니어링** — 에이전트에서 모델을 뺀 나머지 전부를 가리킵니다(Agent = Model + Harness). 코딩 에이전트를 쓰는 입장에서는 두 가지로 나뉩니다.

- **가이드(feedforward)** : 행동하기 전에 방향을 잡아 주는 규칙·문서·스크립트
- **센서(feedback)** : 행동한 뒤 결과를 관측해 스스로 고치게 만드는 신호

각각 다시 **계산형**(컴파일러·정적분석·테스트 — 결정적이고 빠름)과 **추론형**(리뷰 에이전트, LLM 판정 — 느리고 비결정적)으로 나뉩니다.

**루프 엔지니어링** — 에이전트가 반복하는 주기를 설계하는 일입니다. 한 번에 무엇을 할지, 언제 다시 돌릴지, **무엇을 끝난 것으로 볼지**, 막히면 어떻게 복구하거나 사람에게 넘길지를 정합니다. 실패는 대부분 완료 조건이 흐릿한 데서 생깁니다.

**그래프 엔지니어링** — 한 줄기 루프로 감당이 안 되는 일을 여러 에이전트 조직으로 나누는 층입니다. 지휘자–작업자 분업, 작업 그래프, 실행 이력 기록을 통한 재현성 확보가 여기에 들어갑니다.

### 임베디드에 특히 중요한 이유

Fowler는 하네스 중에서도 **"기능이 의도대로 동작하는가"를 검증하는 부분**이 가장 미해결 영역이라고 지적합니다. 임베디드는 여기가 더 어렵습니다. 코드가 컴파일되고 테스트를 통과해도 실제 보드에서는 타이밍이 어긋나고 통신이 끊깁니다. 그래서 이 과정은 **실물 보드를 물려 자동으로 검증하는 루프(HIL)** 를 커리큘럼의 중심 뼈대로 삼았습니다.

## 설계 의도

**1) 캡스톤에서 거꾸로 짰습니다**
센서 → RS-485 → GUI 순서가 그대로 데이터가 흐르는 순서입니다. 앞 차수 결과물이 다음 차수의 재료가 되므로, 8차수에 가면 따로 조립할 필요 없이 시스템이 완성돼 있습니다.

**2) AI 협업을 이론 강의로 빼지 않았습니다**
하네스·루프·그래프를 별도 차수로 몰아 두면 "좋은 얘기지만 우리 일과는 다르다"로 끝납니다. 대신 각 개념이 실제로 필요해지는 순간에 배치했습니다. 가이드는 프로젝트를 처음 열 때(1차), 검증 장치는 첫 드라이버를 확인할 때(2차), 루프는 반복 검증이 지겨워질 때(3차), 그래프는 GUI라는 다른 스택이 병렬로 들어올 때(6차) 등장합니다.

**3) 검증에 시간을 씁니다**
AI가 짠 코드가 하드웨어에서 진짜 도는지 확인하는 시간(실측 검증, 회귀 루프, 장시간 운전 테스트)을 차수마다 넣었습니다. 임베디드에서 AI 코딩이 어긋나는 지점은 대개 이 구간입니다.

**4) 끝나고 남을 것**
과정이 끝나면 코드뿐 아니라 **하네스 템플릿**(가이드 문서 + 검증 스크립트 + 반복 루프)이 남습니다. 이후 사내 임베디드 프로젝트에 그대로 옮겨 쓸 수 있는 형태로 8차수에 정리합니다.

| 대상 설비·레지스터 맵 | 5차수 실연동 범위와 회귀 시나리오를 정하는 기준 |
| 실습 보드·센서 수량 | 팀 편성 인원과 실습 단위(1인/1팀) 결정 |
| 설비 접근 가능 시간 | 5·7차수 실연동과 연속 운전 테스트 일정 배치 |
| GUI 스택 선택 | PySide6 데스크톱이냐 웹 대시보드냐에 따라 6차수 실습이 달라짐 |
| Claude Code 사용 정책 | 사내망에서 쓸 수 있는지, 코드 반출 범위는 어디까지인지 |
| CI 파이프라인 사용 여부 | 3·5차수 회귀 루프를 어디까지 자동화할지 결정 |

## 강사 요건 (구인 공고 보완용)

현재 공고는 요건이 넓어서 지원자가 자기가 적합한지 판단하기 어렵습니다. 이 커리큘럼 기준으로 좁히면 다음과 같습니다.

| 구분 | 구체화된 요건 |
|------|---------------|
| 필수 | ESP-IDF 또는 PlatformIO 기반 ESP32 실무 개발 경험 |
| 필수 | RS-485 물리계층 설계와 Modbus RTU 스택 구현 경험 (라이브러리 가져다 쓴 수준 이상) |
| 필수 | Claude Code 같은 에이전틱 코딩 도구로 실제 펌웨어를 짜고 디버깅해 본 경험 |
| 필수 | FreeRTOS 태스크 설계 경험 |
| 필수 | 임베디드 자동화 테스트(유닛테스트·HIL·CI) 구축 경험 — 3·5차수의 핵심 |
| 선택 | PySide6/Qt 또는 웹 기반 계측 GUI 개발 경험 (없으면 6차수만 보조강사로 분리 가능) |
| 우대 | 서브에이전트·멀티에이전트 워크플로우 운영 경험 (6~7차수) |
| 우대 | 산업 현장 설비 연동 프로젝트 경험 |

**분업 옵션** — 6차수 GUI를 별도 강사로 분리하면 후보 풀이 넓어집니다. 임베디드 주강사가 1~5·7~8차수, GUI 강사가 6차수를 맡는 구조를 권합니다.

**공고 문구 보완 제안** — "AI 코딩 도구 활용 경험"만 써 두면 후보가 스스로를 걸러내지 못합니다. "에이전트에게 줄 가이드와 검증 장치를 직접 설계해 본 경험", "빌드–플래시–검증을 자동으로 반복시키는 루프를 구성해 본 경험"처럼 행위 단위로 쓰면 지원 정확도가 올라갑니다.
