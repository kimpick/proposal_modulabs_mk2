# 크레딧 런웨이 모델 — Tier1~4 번레이트 프레임

> 작성일: 2026-08-13 · 버전 v1 · 연결 문서: [토큰절감_5차원_리서치.md](토큰절감_5차원_리서치.md)
> 목적: "월말에 크레딧이 소진돼서 일을 못 한다"는 고객 페인을 **측정 가능한 지표**로 바꾸고, 5차원 레버가 그 지표를 얼마나 움직이는지 계산하는 틀
> ⚠️ **수량은 전부 변수로 비워두었습니다.** 고객 확인 문항 2번(티어별 크레딧 수량 + 환산율 표) 회신 즉시 채워 넣으면 시뮬레이션이 완성됩니다.

---

## 1. 왜 "절감"이 아니라 "런웨이"인가

기존 토큰 최적화 담론의 지표는 **비용(달러)**입니다. 삼성 MX 환경의 지표는 다릅니다.

```
크레딧 런웨이 = 남은 크레딧 ÷ 일 평균 소모
```

이 값이 **남은 일수보다 작으면 월말 이전에 고갈**합니다. 고객이 겪는 문제를 정확히 이 한 줄이 설명합니다.

### 이 지표가 갖는 성질

| 성질 | 내용 | 함의 |
|---|---|---|
| **주기적** | 매월 1일 리셋 | 30일 단위로 계획·조정. 연속 예산이 아님 |
| **이월 불가** | 업계 크레딧 제도 관행 (Perplexity·Miro 등)에서 미사용분 소멸 | **과소 사용도 손실**. 목표는 아끼기가 아니라 완주 |
| **비선형 환산** | 크레딧↔토큰 비율이 모델·서비스 방식마다 다름 | **"무엇으로 부르는가"가 곧 환산율 선택** |
| **개인 귀속** | Tier1~4 개인별 차등 | 조직 평균이 아니라 **개인별 런웨이**를 봐야 함 |

> ※ 이월 불가는 타 벤더 크레딧 제도의 일반 관행에 근거한 **추정**입니다. 삼성 사내 정책은 고객 확인 필요 (§6 미확인 3번).

## 2. 기본 산식

### 2.1 정의

| 기호 | 의미 | 확보 상태 |
|---|---|---|
| `C_tier` | 해당 티어의 월 크레딧 총량 | ❌ 미확인 |
| `D` | 월 근무일 수 (기본 20일 가정) | 가정값 |
| `d` | 경과 근무일 | 실측 |
| `U` | 현재까지 사용한 크레딧 | 실측 (가시화 필요 → 5차원 모니터링) |
| `R = C_tier − U` | 남은 크레딧 | 계산 |
| `B = U / d` | 실제 일 번레이트 | 계산 |
| `B_target = C_tier / D` | 목표 일 번레이트 (기준선) | 계산 |
| `L = R / B` | **런웨이 (남은 일수)** | 계산 |

### 2.2 판정

```
L ≥ (D − d)   →  안전 — 월말까지 완주 가능
L <  (D − d)  →  경고 — 이 속도면 (D − d − L)일 먼저 고갈
```

### 2.3 필요 절감률

경고 상태에서 완주하려면 번레이트를 얼마나 낮춰야 하는가:

```
필요 절감률 = 1 − ( R / ((D − d) × B) )
```

**예시 (수치는 예시일 뿐, 실제 크레딧 수량 확인 후 대체)**
근무일 20일 중 12일 경과, 월 크레딧의 85%를 소진했다면
- `B = 0.85 / 12 = 0.0708` (일 7.08%)
- `R = 0.15`, 남은 일수 `= 8`
- `L = 0.15 / 0.0708 = 2.1일` → **8일 남았는데 런웨이는 2.1일. 5.9일 먼저 고갈.**
- 필요 절감률 `= 1 − (0.15 / (8 × 0.0708)) = 1 − 0.265 = **73.5%**`

→ 이 시점에서 73.5%를 줄이는 건 사실상 사용 중단입니다. **런웨이 관리는 월말이 아니라 월초에 해야 한다**는 것이 이 모델의 첫 번째 교훈이며, 임원 세미나의 핵심 시각 자료 후보입니다.

## 3. 환산율 층 — 크레딧은 토큰이 아니다

고객이 명시한 조건: **"크레딧이 모델마다, 서비스 방식마다 Token과 대응되는 비율이 다름"**

이 층이 5차원 중 **3. 하네스(모델 라우팅)**를 최대 레버로 만드는 이유입니다. 같은 토큰 수를 써도 무엇으로 부르느냐에 따라 크레딧 소모가 달라집니다.

### 3.1 환산율 표 (확인 후 채울 골격)

| 모델 | 서비스 방식 | 입력 크레딧/1K토큰 | 출력 크레딧/1K토큰 | 캐시읽기 배율 | 비고 |
|---|---|---|---|---|---|
| 상위 모델 | 대화형 | ❌ | ❌ | ❌ | |
| 상위 모델 | 에이전트/코딩 | ❌ | ❌ | ❌ | |
| 경량 모델 | 대화형 | ❌ | ❌ | ❌ | |
| 경량 모델 | 에이전트/코딩 | ❌ | ❌ | ❌ | |
| (기타) | | | | | |

### 3.2 이 표가 채워지면 계산 가능해지는 것

1. **라우팅 차익** — 저난도 작업을 경량 모델로 돌렸을 때의 실제 크레딧 절감폭
2. **출력 페널티** — 출력 크레딧이 입력의 몇 배인지 (일반 토큰 단가는 5~10배, 크레딧 환산은 별개일 수 있음)
3. **캐시 가치** — 캐시 읽기 배율이 크레딧 층에도 적용되는지. 적용되면 세션 유지 전략이, 미적용이면 세션 분리 전략이 유리
4. **방식 차익** — 같은 모델이라도 대화형과 에이전트형의 환산율 차이

> **설계 주의**: 3번 결과에 따라 §4의 권장 습관이 뒤집힐 수 있습니다. 캐시 할인이 크레딧 층에 반영되지 않는다면 "세션을 오래 유지해 캐시 히트를 노린다"는 조언은 삼성 환경에서 **역효과**입니다. 확인 문항 2번이 🔴 인 이유입니다.

## 4. 5차원 레버 → 번레이트 감축 매핑

각 레버가 `B`(일 번레이트)를 낮추는 경로입니다. 감축률은 문헌 근거이며, 삼성 환경 실측치는 본과정 before/after 랩에서 산출합니다.

| 레버 | 차원 | 번레이트에 작용하는 방식 | 문헌 감축률 |
|---|---|---|---|
| 3요소 선지정 | 1 프롬프트 | 재작업 왕복 횟수 자체를 줄임 → 요청 수 감소 | 재작업이 전체의 ~59% |
| 출력·사고 상한 | 1 프롬프트 | 요청당 출력 토큰 감소 (단가 5~10배 구간) | 30~50% |
| 작업 단위 세션 분리 | 2 컨텍스트 | 요청당 입력 토큰 증가 곡선을 끊음 | (누적 구조 제거) |
| 온디맨드 지침 로드 | 2 컨텍스트 | 세션 시작 시 고정 비용 감소 | — |
| 컨텍스트 편집·컴팩션 | 2 컨텍스트 | 장기 세션의 히스토리 부피 억제 | 최대 84% (100턴 기준) |
| **난이도별 모델 라우팅** | **3 하네스** | **환산율이 낮은 경로로 트래픽 이동** | **40~85%** |
| 도구 최소화 | 3 하네스 | 매 턴 고정 오버헤드 감소 | 사례상 컨텍스트 72% 점유 해소 |
| 서브에이전트 격리 | 3 하네스 | 장황한 출력이 본 대화에 누적되지 않음 | 9K vs 15K |
| 종료조건·재시도 상한 | 4 루프 | 폭주 이벤트의 꼬리 위험 제거 | 낭비율 80%+ → 5% 미만 |
| 소모 가시화·알림 | 5 모니터링 | 위 전부를 **작동시키는 전제** | (간접) |

> **루프 차원 주의** — 이 레버는 대화형 제품의 설정이 아니라 **자동화·프레임워크 층**에 존재합니다. 임원이 웹 채팅만 사용한다면 개인 레버가 없으므로 조직 결정 사항으로 다뤄야 합니다. (상세: [벤더별_명령_부록.md](벤더별_명령_부록.md) §5)

### 4.1 결합 효과 주의

감축률은 **곱해지지 않습니다**. 세션 분리로 이미 히스토리를 줄였다면 컴팩션의 추가 효과는 작아집니다. 교육에서 "40% + 50% = 90% 절감"으로 제시하면 안 되며, **실측 랩으로 결합 효과를 직접 확인**시키는 것이 본과정 설계의 근거입니다.

## 5. 월말 고갈 시나리오 (임원 세미나 시각 자료 후보)

동일 사용자·동일 업무량을 두 조건으로 시뮬레이션합니다. **크레딧 수량 확인 후 실수치로 대체**하며, 그 전까지는 티어 크레딧을 100%로 정규화해 표현합니다.

### 5.1 시나리오 A — 현재 습관

| 근무일 | 누적 소모(%) | 상태 |
|---|---|---|
| 5 | 35 | |
| 10 | 71 | |
| 12 | 85 | ⚠️ 경고 |
| **14** | **100** | 🔴 **고갈 — 6일 남기고 중단** |

### 5.2 시나리오 B — 4개 레버 적용

적용 레버: 3요소 선지정 · 세션 분리 · 모델 라우팅 · 소모 확인 습관 (§8 매트릭스 상위 4개)

| 근무일 | 누적 소모(%) | 상태 |
|---|---|---|
| 5 | 20 | |
| 10 | 41 | |
| 15 | 61 | |
| **20** | **82** | ✅ **완주 + 18% 여유** |

### 5.3 이 슬라이드가 전달하는 것

- 문제는 "비싸다"가 아니라 **"14일차에 멈춘다"**
- 해법은 절제가 아니라 **번레이트 조정**
- 필요한 감축폭은 극적이지 않음 — **상위 4개 레버만으로 충분**
- 단, 조정은 **월초에** 해야 함 (§2.3 — 12일차에는 73.5% 감축이 필요해짐)

> ⚠️ 위 수치는 5차원 문헌 감축률로부터 역산한 **예시 곡선**입니다. 고객 제출 자료에는 반드시 "예시" 표기를 하거나, 실제 크레딧 수량 확인 후 실수치로 교체해야 합니다.

## 6. 미확인 사항

| # | 항목 | 이 문서에서 막히는 것 | 위험도 |
|---|---|---|---|
| 1 | Tier1~4 각각의 월 크레딧 수량 | §2 산식의 `C_tier`, §5 시뮬레이션 실수치 | 🔴 |
| 2 | 모델별·서비스방식별 크레딧↔토큰 환산율 | §3 표 전체. **캐시 할인의 크레딧 반영 여부에 따라 §4 권장이 뒤집힐 수 있음** | 🔴 |
| 3 | 미사용 크레딧 이월 정책 | §1 "과소 사용도 손실" 논리의 성립 여부 | 🟠 |
| 4 | 사용자가 자기 소모량(`U`)을 실시간으로 볼 수 있는가 | 산식 전체가 계산 불가 — **모델이 아니라 사후 분석에 그침** | 🔴 |
| 5 | 티어 배정 기준 (직급? 직무? 신청?) | 조직 레버(티어 재배분) 제안 가능 여부 | 🟡 |
| 6 | 월 근무일 `D` 기준 (20일 가정 타당한가) | 기준선 정확도 | 🟡 |

> 4번이 🔴 인 이유: 소모량을 볼 수 없다면 이 모델은 **사후 부검**은 되지만 **조종**은 못 합니다. 5차원 중 모니터링 모듈의 설계가 여기서 갈립니다.
