## 1. 프레임 전환 — 비용 이슈가 아니라 품질 이슈

지금까지 이 프로젝트는 **크레딧 런웨이**(월말 고갈)를 축으로 삼았습니다. 그것이 삼성 MX의 **비즈니스 페인**입니다. 그런데 이 프레임만으로는 임원의 자연스러운 반론을 막지 못합니다.

> *"토큰을 아끼면 결국 AI가 덜 알고 답하는 것 아닌가? 품질을 깎아 비용을 사는 것 아닌가?"*

**답은 '아니오'입니다. 오히려 반대입니다.** 컨텍스트를 줄이면 출력 품질이 **올라갑니다**. 이것이 이 문서의 논지이며, 두 프레임은 다음과 같이 맞물립니다.

| 프레임 | 역할 | 대상 |
|---|---|---|
| **크레딧 런웨이** | 왜 지금 해야 하나 (비즈니스 페인) | 삼성 MX 고유 상황 |
| **컨텍스트 품질** | 줄여도 되나? → **줄이면 더 좋아진다** | 보편 원리, 반론 차단 |

→ 세미나 논리 흐름: **"월말에 멈춘다"(문제) → "줄이면 품질도 좋아진다"(반론 차단) → "이렇게 줄인다"(5차원)**

## 2. Context Rot — 원 연구와 2026년 현재 유효성

> ⚠️ **인용 주의** — 이 절의 원 연구는 **2025년 7월** 발표이며 당시 세대 모델을 대상으로 합니다. 2026년 8월 현재 프런티어 모델에서는 **일부 결과가 더 이상 성립하지 않습니다.** 아래 2.3에서 무엇이 바뀌고 무엇이 남았는지 구분했습니다. **고객 자료에는 2.3의 현재 수치를 쓰고, 2.1은 "원리를 규명한 연구"로만 인용하십시오.**

### 2.1 원 연구 (2025-07-14)

**Context Rot: How Increasing Input Tokens Impacts LLM Performance**
Kelly Hong · Anton Troynikov · Jeff Huber (Chroma), **2025년 7월 14일 발표**

**대상 모델 (발표 시점 기준 SOTA)**: GPT-4.1, Claude 4, Gemini 2.5, Qwen3 등 **18개**
→ 2026년 8월 현재 기준으로는 **모두 이전 세대입니다.**

**방법**: 과제 난이도를 고정하고 **입력 길이만** 변화시켜 길이 단일 효과를 분리 측정

**결과**
- 18개 모델 **전부에서 입력이 길어질수록 F1 단조 감소**
- 검색·복제 같은 단순 과제에서조차 신뢰도 저하
- 모델은 컨텍스트를 **균일하게 사용하지 않음**

### 2.2 이 연구가 규명한 메커니즘 (여전히 유효)

메커니즘 자체는 트랜스포머 구조에서 비롯되므로 **모델 세대가 바뀌어도 사라지지 않습니다.** 완화될 뿐입니다.

| 메커니즘 | 내용 | 2026 상태 |
|---|---|---|
| **Lost-in-the-middle** | 정답이 중간에 있으면 정확도 하락 | 완화됐으나 잔존 |
| **주의 희석 (attention dilution)** | 트랜스포머의 이차 관계에서 비롯 | **구조적 — 잔존** |
| **방해자 간섭 (distractor interference)** | 의미는 비슷하나 무관한 내용이 정답을 밀어냄 | **잔존 — 실무에서 가장 중요** |

### 2.3 ★ 2026년 8월 현재 — 무엇이 바뀌었나

**한 줄 요약: 벤더들이 쉬운 벤치마크는 고쳤지만, 실제 업무를 닮은 과제는 여전히 저하됩니다.**

#### 해결된 것 — 단일 정보 검색

| 모델 | 1M 컨텍스트 단일 니들 |
|---|---|
| Gemini 3 | **99%** |
| GPT-5.5 | **96%** |

→ *"긴 문서에서 사실 하나 찾기"* 는 사실상 해결됐습니다.
→ **2025년 Chroma의 "단순 검색조차 틀린다"를 2026년 자료에 그대로 인용하면 안 됩니다.**

#### 남아 있는 것 — 여러 사실을 동시에 다루기

| 모델 | 1M, **8개 니들** (현실적 시나리오) |
|---|---|
| Gemini 3 | **89%** |
| GPT-5.5 | **74%** |
| DeepSeek V4 Pro | **41%** |

→ 실무는 "사실 하나 찾기"가 아니라 **여러 근거를 모아 종합하기**입니다. 그 과제에서는 격차가 그대로입니다.

#### 실효 컨텍스트

> **NVIDIA RULER 벤치마크 기준, 대부분 모델의 실효 컨텍스트는 광고 용량의 50~65%**
> 1M이면 실제 신뢰 가능한 구간은 **500~650K**

#### 모델별 편차가 커졌다

2025년에는 "전 모델이 저하"였지만, 2026년에는 **모델에 따라 크게 갈립니다.**
- Claude Opus 4.6은 1M에서 높은 신뢰도를 유지한다는 보고
- GPT-5.1은 8K에서 90% → 256K에서 50% 미만으로 저하
- 반면 **GPT-5.2는 20만 단어 전 구간에서 near-100%** 달성 (4개 사실 회수)
- Michelangelo 평가: GPT·Claude는 짧은 컨텍스트에서 우수하나 **더 빠르게 감쇠**, Gemini는 낮은 기준선에서 **완만히 감쇠**

→ **"모든 모델이 나쁘다"가 아니라 "모델과 과제에 따라 다르다"가 2026년의 정확한 서술입니다.**

### 2.4 그래도 논점이 유효한 이유 — 벤더 자신의 행동

가장 강한 증거는 벤치마크가 아니라 **벤더가 실제로 무엇을 만드는가**입니다. 2026년 8월 현재 Anthropic 공식 문서 기준:

| 사실 | 함의 |
|---|---|
| **Sonnet 5는 1M 창인데도 약 967K에서 자동 압축** | 벤더 스스로 창을 끝까지 쓰지 않음 |
| `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 제공 — *"컨텍스트를 제한해야 하는 배포에 유용"* | **창을 좁히는 것이 공식 지원 기능** |
| `/compact` · `/btw` · `/autocompact` · 컨텍스트 편집 · 도구 정의 지연 로딩 계속 개발 | 긴 컨텍스트가 해결됐다면 만들 이유가 없음 |
| 공식 문서가 *"CLAUDE.md 200줄 이하 유지"*, *"작업 바뀌면 `/clear`"* 를 계속 권고 | 권고가 철회되지 않음 |

**컨텍스트 창이 커진 것과 컨텍스트 관리가 불필요해진 것은 다릅니다.** 전자는 사실이고 후자는 아닙니다.

### 2.5 원칙 한 줄 (세대 무관)

> **"원하는 결과를 낼 확률을 최대화하는, 가장 작은 고신호(high-signal) 토큰 집합을 찾는 것."** — Anthropic

목표는 "많이 넣기"도 "적게 넣기"도 아니라 **신호 대 잡음비를 높이는 것**입니다. 토큰 절감은 그 부산물입니다. 이 원칙은 모델 성능과 무관하게 성립합니다.

### 2.6 임원 세미나용 문구 (갱신본)

> **[임원30분] — 2026년 8월 기준으로 이렇게 말해야 합니다**
>
> *"컨텍스트를 줄이는 건 AI를 덜 똑똑하게 만드는 게 아닙니다.*
> *모델들이 '긴 문서에서 사실 하나 찾기'는 거의 완벽해졌습니다 — 96~99%.*
> *그런데 **여러 근거를 동시에 모아 종합하는 일**, 그러니까 우리가 실제로 시키는 일에서는 **74~89%**로 떨어집니다.*
> *그리고 벤치마크 기준 모델이 신뢰성 있게 쓰는 건 광고된 창의 **50~65%**입니다. 100만이라고 쓰여 있어도 실제로는 50~65만입니다.*
> *크레딧을 아끼는 일과 정답률을 올리는 일이 같은 방향인 이유입니다."*

**이 버전이 2025년 버전보다 강한 이유**: "AI가 못 한다"가 아니라 **"광고와 실제가 다르다"**는 메시지이고, 임원에게는 후자가 훨씬 잘 꽂힙니다. 또한 반박 가능성이 낮습니다 — 단일 검색이 좋아진 것을 먼저 인정하고 들어가기 때문입니다.

> ⚠️ **강사 주의** — 청중이 "요즘 모델은 다르지 않나요?"라고 물으면 **맞다고 인정하고 2.3의 구분(단일 검색 해결 / 다중 종합 미해결)으로 답하십시오.** 2025년 결과를 방어하려 들면 신뢰를 잃습니다.

## 3. 실무 4레버 — Write / Select / Compress / Isolate

2026년 컨텍스트 엔지니어링의 표준 프레임입니다. 이 프로젝트의 **5차원 중 "2. 컨텍스트"의 하위 구조**로 씁니다.

| 레버 | 무엇 | 실무 조작 (플레이북 대응) |
|---|---|---|
| **Write** | 컨텍스트 **밖에** 기록해 두고 필요할 때 부른다 | 결정 기록 후 종료(§2-4), 외부 메모리 파일, 요약본 만들기(§2-3) |
| **Select** | 지금 이 작업에 **필요한 것만** 넣는다 | 온디맨드 지침 로드(§2-7), 표적 읽기, 도구 끄기(§3-2) |
| **Compress** | 이미 들어온 것을 **압축**한다 | `/compact` 보존 지시(§2-5), 툴 출력 정리(§3-5) |
| **Isolate** | 작업을 **분리**해 노이즈가 서로를 오염시키지 않게 한다 | 세션 분리(§2-2), `/btw`(§2-12), 서브에이전트(§3-3) |

**Isolate가 특히 중요한 이유**: Context Rot의 세 번째 메커니즘이 **방해자 간섭**입니다. 한 작업의 실패한 시도가 다른 작업의 컨텍스트에 남아 있으면, 그것이 그대로 방해자로 작동합니다. **분리는 절감 기법이자 품질 기법입니다.**

## 4. API·스킬 제작 레벨 (심화)

직접 스킬·에이전트를 만드는 경우에만 해당합니다. 본과정 심화 트랙 또는 개발자 대상 후속 과정 소재입니다.

| 기법 | 내용 | 효과 |
|---|---|---|
| **서버사이드 compaction** (`compact_20260112`) | 컨텍스트 한계 근접 시 과거 내용을 자동 요약. 벤더 권장 기본 전략 | 사실상 무한 대화 |
| **Memory tool + context editing 조합** | compaction은 활성 컨텍스트를 작게 유지, memory는 요약에서 살아남아야 할 정보를 파일로 보존 | context editing 단독 **+29%**, memory 병용 **+39%** |
| **Prompt caching** | 반복 프리픽스 재사용 | 캐시 읽기 정가의 약 10%. 수명: 구독 1시간 / API 기본 5분 |
| **Code execution with MCP** | 툴을 JSON 스키마 대신 **코드로 노출** | 컨텍스트 오버헤드 **98.7% 감소** 보고 |
| **Message Batches API** | 비동기 대량 처리 | 최대 **50%** 절감 |

## 5. 연구 프론티어 — ACE (교육 콘텐츠용)

**Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models**
Qizheng Zhang 외, Stanford · SambaNova · UC Berkeley · **ICLR 2026** 채택 (arXiv 2510.04618)

### 5.1 3역할 구조

컨텍스트를 고정된 프롬프트가 아니라 **사용하며 개선되는 살아있는 문서**로 취급합니다.

| 역할 | 하는 일 |
|---|---|
| **Generator** | 추론 궤적(reasoning trajectory)을 생성 |
| **Reflector** | 성공과 실패에서 구체적 교훈을 추출 |
| **Curator** | 교훈을 **델타 항목**으로 합성해 기존 컨텍스트에 병합 |

병합은 **LLM이 아닌 경량 결정론적 로직**이 수행합니다. 업데이트가 항목 단위로 국소화되어 있어 **여러 델타를 병렬 병합**할 수 있고, 대규모 배치 적응이 가능합니다.

### 5.2 이 논문이 명명한 두 실패 모드

교육에서 가장 잘 먹히는 부분입니다. 수강생이 **자기 경험으로 즉시 알아봅니다.**

| 실패 모드 | 증상 |
|---|---|
| **Brevity bias** | 반복 요약할수록 모델이 **압축하며 디테일을 잃음** |
| **Context collapse** | 누적된 지식이 **그럴듯하지만 실행 불가능한 일반론으로 표류** |

→ *"AI에게 계속 요약시켰더니 어느 순간부터 맞는 말인데 쓸모없는 소리만 한다"* 는 현상의 정체입니다.

### 5.3 성능

에이전트 과제 **+10.6%**, 금융 과제 **+8.6%**

> **강의용 메시지**: **"모델이 똑똑해진 것이 아니라 컨텍스트가 좋아진 것입니다."**
> 같은 모델, 같은 가중치인데 컨텍스트를 어떻게 다루느냐로 10% 차이가 납니다. 컨텍스트 엔지니어링이 왜 별도의 기술 영역인지를 한 문장으로 설명합니다.

### 5.4 실무 시사 — 통짜 재작성 대신 국소 증분

지침 파일이나 프롬프트를 개선할 때, **전체를 다시 쓰게 하는 것이 아니라 항목 단위로 더하고 빼는 방식**이 열화를 막습니다. 사내 지침·스킬 라이브러리 운영에도 그대로 적용됩니다.
