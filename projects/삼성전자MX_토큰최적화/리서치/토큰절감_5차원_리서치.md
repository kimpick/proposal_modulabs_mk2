## 0. 리서치 요약

### 핵심 발견 5가지

1. **가장 큰 낭비는 생성이 아니라 되돌리기다.** 리뷰·재작업 루프가 전체 토큰의 약 **59%**를 소모합니다 [업계]. 프롬프트를 한 번에 맞히는 것이 다른 모든 기법을 합친 것보다 효과가 큽니다.
2. **대화가 길어지면 가만히 있어도 비싸진다.** 대화형 AI는 매 요청마다 전체 대화를 다시 보냅니다. 하루 종일 열어둔 세션에서는 한 줄 질문도 전체 히스토리 분량을 청구합니다 [공식].
3. **캐시는 입력만 깎아준다.** 프롬프트 캐시는 입력 토큰을 최대 90% 할인하지만 **출력 토큰에는 할인이 없습니다** [업계]. 게다가 출력 토큰은 입력보다 5~10배 비쌉니다 [업계]. → 출력 통제는 캐시와 독립된 별개 레버입니다.
4. **모델 선택이 단일 최대 레버다.** 난이도별 모델 라우팅만으로 비용 **40~85%** 절감, 품질은 **90~95%** 유지 [업계]. 삼성 환경은 크레딧↔토큰 환산율이 모델마다 달라 이 레버의 효과가 더 커집니다.
5. **안 보이는 것은 관리되지 않는다.** 월말 고갈은 사건이 아니라 한 달간 누적된 낭비의 **결과**입니다. 소모량 가시화가 나머지 4차원을 작동시키는 전제조건입니다.

### 5차원 지도

| # | 차원 | 지배적 낭비 | 대표 레버 | 임원 한 문장 |
|---|---|---|---|---|
| 1 | **프롬프트** | 재작업 왕복, 출력 폭주 | 의도·수용기준·출력형식 선지정 | "한 번에 맞히면 재작업 크레딧은 0" |
| 2 | **컨텍스트** | 히스토리 누적 재전송, 상시 로드 지침 | 세션 분리, 컴팩션 타이밍, 온디맨드 로드 | "책상에 서류를 쌓을수록 매번 전부 다시 읽는다" |
| 3 | **하네스** | 무거운 모델로 잔일, 도구 과다 주입 | 모델 라우팅, 도구 최소화, 서브에이전트 격리 | "회의에 전원을 부르지 않는다" |
| 4 | **루프** | 재시도 폭주, 종료조건 부재 | 반복 상한, 무진전 감지, 승인 게이트 | "끝나는 조건을 안 정하면 무한히 청구된다" |
| 5 | **모니터링** | 소모 무자각 → 월말 고갈 | 번레이트 기준선, 귀속 분석, 알림 | "런웨이를 못 보면 착륙을 못 한다" |

## 1. 문제 재정의 — "절감"이 아니라 "크레딧 런웨이"

### 1.1 고객 상황

- 사내 엔터프라이즈 버전 도입 후 토큰 소모량 체감 **2~4배** 증가
- 임직원별 **Tier 1~4** 차등, 월 단위 Credit 부여, **매월 1일 리셋**
- 크레딧↔토큰 환산율이 **모델마다, 서비스 방식마다 다름**
- **월말이 다가오면 크레딧 소진으로 서비스를 못 쓰는 경우 발생**

### 1.2 이것이 바꾸는 것

일반적인 토큰 최적화 담론은 **원가 절감**(달러)을 목표로 합니다. 삼성 MX 환경은 다릅니다.

| | 일반 담론 | 삼성 MX 실제 |
|---|---|---|
| 단위 | 달러 | **크레딧** (모델·방식별 환산율 상이) |
| 실패 모습 | 청구서가 비쌈 | **월말에 일을 못 함** |
| 목표 | 지출 최소화 | **같은 크레딧으로 더 많은 산출** |
| 시간축 | 연속적 | **매월 1일 리셋되는 30일 사이클** |
| 이월 | — | 업계 관행상 **미사용 크레딧은 이월되지 않음** [업계] |

→ **KPI는 크레딧 런웨이: 내 티어 크레딧으로 한 달을 완주하는가.**

이 재정의가 만드는 세 가지 설계 결론:

1. **"덜 쓰기"는 오답이다.** 아껴서 남기면 이월도 안 되고 성과도 없습니다. 목표는 효율(산출÷크레딧)이지 절대량이 아닙니다.
2. **환산율 선택이 곧 절감이다.** 같은 일을 어떤 모델로 어떤 방식으로 부르느냐가 크레딧 소모를 결정합니다 → **3. 하네스 차원이 최대 레버**.
3. **모니터링이 옵션이 아니다.** 30일 사이클에서 번레이트를 모르면 조종이 불가능합니다 → **5. 모니터링이 나머지의 전제조건**.

### 1.3 왜 2~4배가 되었나 — 가설 4개

고객이 제품을 특정해주기 전까지는 가설입니다. 다만 네 가설 모두 5차원 프레임 안에서 설명됩니다.

| 가설 | 메커니즘 | 해당 차원 |
|---|---|---|
| **에이전트형 사용 전환** | 채팅은 1턴 1왕복이지만, 에이전트는 파일 읽기·도구 호출·다단 추론을 한 요청에 담고 그 결과를 다시 보냄. 코딩 세션 1회가 채팅 하루치를 넘을 수 있음 [공식] | 3, 4 |
| **긴 세션 상시 유지** | 대화 전량이 매 요청에 재전송. 세션을 안 닫으면 소모가 대화 길이에 비례해 증가 [공식] | 2 |
| **사고(reasoning) 토큰** | 확장 사고는 **출력 토큰으로 과금**되며 기본 예산이 요청당 수만 토큰에 이를 수 있음 [공식] | 1, 3 |
| **도구·지침 상시 주입** | 지침 파일·도구 스키마가 매 턴 컨텍스트에 포함 | 2, 3 |

> **[임원30분]** — "2~4배는 서비스가 비싸진 게 아니라, **쓰는 방식이 채팅에서 에이전트로 바뀐 결과**입니다. 방식을 알면 되돌릴 수 있습니다."

## 2. 공통 원리 — 토큰이 흐르는 구조

5차원에 들어가기 전, 모든 차원이 공유하는 기반입니다.

### 2.1 토큰은 한 종류가 아니다

| 종류 | 상대 단가 | 특징 |
|---|---|---|
| 입력 (input) | 1× | 캐시 할인 대상 |
| **출력 (output)** | **5~10×** [업계] | **캐시 할인 대상이 아님** |
| 캐시 쓰기 | 1.25× (5분) / 2× (1시간) [업계] | 첫 회 프리미엄 |
| 캐시 읽기 | **0.1×** [업계] | 90% 할인 |
| 사고 (thinking) | 출력과 동일 | 출력 토큰으로 과금 [공식] |

**함의**: 절감 논의가 "입력 줄이기"에 쏠려 있지만, 단가가 5~10배인 출력과 사고 토큰이 실질 지배 변수인 경우가 많습니다.

### 2.2 대화형 AI의 누적 구조

> "Claude Code sends your full conversation with every request, and each time Claude uses tools it sends another request carrying that batch of tool results. … a one-line question in a session that has been open all day still draws usage for the whole conversation." — [공식] Anthropic

이것이 **차원 2(컨텍스트)의 물리적 근거**입니다. 대화 길이가 N일 때 총 소모는 N에 비례하는 게 아니라 **N²에 가깝게** 증가합니다. 매 턴마다 그때까지의 전량을 다시 보내기 때문입니다.

### 2.3 긴 세션에서 소모가 오르는 6가지 이유 [공식]

Anthropic이 공식 문서에 명시한 목록입니다. 그대로 교육 자료로 쓸 수 있습니다.

1. **긴 컨텍스트** — 전체 대화를 매 요청에 전송
2. **캐시 미스** — 캐시 수명(구독 1시간 / 크레딧·API 5분)을 넘겨 쉬면 다음 첫 요청이 전체 컨텍스트를 재처리
3. **예약 작업** — 세션이 유휴여도 주기마다 전체 컨텍스트를 보냄
4. **세션 간 메시지** — 다른 세션의 메시지가 새 턴으로 배달되며 전체 컨텍스트 전송
5. **에이전트 팀원** — 각 팀원이 종료 전까지 계속 소모
6. **컴팩션 자체** — `/compact`는 요약할 대화를 읽으므로 그 자체가 큰 요청. 연속성이 필요 없다면 **`/clear`는 비용이 0**

> **[임원30분]** — 2번(캐시 미스)이 임원에게 가장 반직관적입니다. **"점심 먹고 와서 던진 첫 질문이 오전 내내 쌓은 대화 전체를 다시 청구한다."**

## 3. 차원 1 — 프롬프트 엔지니어링

### 3.1 낭비 메커니즘

| 메커니즘 | 설명 | 정량 |
|---|---|---|
| **재작업 왕복** | 모호한 지시 → 빗나간 결과 → 재지시 → 재생성. 각 왕복이 그때까지의 전체 컨텍스트를 재전송 | **리뷰·재작업 루프가 전체 토큰의 약 59%** [업계] |
| **출력 폭주** | 길이·형식 제약이 없으면 모델이 장문으로 답함. 출력은 입력의 5~10배 단가 | 출력 길이 통제 + 히스토리 요약으로 **30~50%** 절감 [업계] |
| **광범위 스캔 유발** | "이 코드베이스를 개선해줘" 같은 요청은 광범위 탐색을 유발. "auth.ts의 login 함수에 입력 검증 추가"는 최소 파일 읽기로 끝남 [공식] | — |
| **과잉 사고** | 단순 작업에도 확장 사고가 기본 작동, 요청당 수만 출력 토큰 소모 가능 [공식] | — |
| **장황한 시스템 지침** | 시스템 프롬프트의 모든 토큰은 매 호출마다 과금 | 간결화로 기준 입력 사용량 **30~50%** 절감 [업계] |

### 3.2 레버 (벤더 중립)

**L1-1. 3요소 선지정** — 요청에 항상 세 가지를 포함
- **의도**: 무엇을 왜 (목적)
- **수용기준**: 무엇이 충족되면 완료인가 (검증 가능한 형태)
- **출력형식**: 어떤 모양으로 (형식 + 분량 상한)

**L1-2. 검증 타깃 동봉** — 테스트 케이스·기대 출력·스크린샷을 함께 주면 모델이 스스로 검증해 재작업 요청 전에 잡아냄 [공식]

**L1-3. 출력 상한 이중 설정** — 프롬프트에 "50단어 이내" + API/설정에 최대 토큰 상한. 둘 중 하나만으로는 새어나감 [업계]

**L1-4. 사고 강도 조절** — 단순 작업은 추론 강도를 낮춤. 사고 토큰은 출력 단가 [공식]

**L1-5. 계획 우선** — 복잡한 작업은 실행 전 계획 승인 단계를 거침. 방향이 틀렸을 때의 값비싼 재작업을 예방 [공식]

**L1-6. 조기 중단** — 방향이 어긋나면 즉시 중단. 끝까지 두고 보면 그 출력 전량이 과금됨 [공식]

**L1-7. 점진 검증** — 한 덩어리 요청 대신 작게 나눠 각 단계 확인. 오류가 쌀 때 잡힘 [공식]

### 3.3 교육 배치

- **`[임원30분]`** — **"토큰의 절반 이상은 만드는 데가 아니라 되돌리는 데 쓰인다"** (59% 수치). 임원이 가장 즉시 이해하고 즉시 바꿀 수 있는 단 하나의 습관 = **3요소 선지정**.
- **`[실무자실습]`** — 동일 과제를 (a) 한 줄 모호 지시, (b) 3요소 명시 지시로 각각 실행하고 **소모 토큰을 실측 비교**. 절감률을 수강생이 직접 산출.

## 4. 차원 2 — 컨텍스트 엔지니어링

### 4.1 낭비 메커니즘

| 메커니즘 | 설명 | 정량 |
|---|---|---|
| **히스토리 누적 재전송** | 매 요청이 전체 대화를 실어 보냄 (§2.2) | 장기 세션에서 지배적 |
| **캐시 미스** | 캐시 수명 초과 후 첫 요청이 전체 컨텍스트 재처리. 수명은 구독 1시간, 크레딧·API 5분 [공식] | 캐시 읽기 0.1× → 정가 1× (**10배**) |
| **상시 로드 지침 파일** | 프로젝트 지침 파일은 세션 시작 시 컨텍스트에 로드. 무관한 작업 중에도 그 토큰이 존재 [공식] | 5,000토큰 지침 = 한 글자 치기 전에 5,000토큰 [업계] |
| **@import 착시** | 파일을 쪼개도 시작 시 함께 로드되면 절감 효과 없음 | — (사내 자산에서 확인) |
| **컴팩션 자체 비용** | 요약하려면 먼저 읽어야 함 → 큰 컨텍스트의 컴팩션은 그 자체가 큰 요청 [공식] | — |
| **컨텍스트 포화 → 품질 저하** | 포화 시 자동 압축이 과거 결정을 잃어버려 환각·설계 망각 발생 → 재작업 유발 | (사내 7-8월 트랙2 M3에서 이미 다룸) |

### 4.2 레버 (벤더 중립)

**L2-1. 작업 단위 세션 분리** — 무관한 작업으로 넘어가면 세션을 새로 시작. 지난 컨텍스트는 이후 모든 메시지에서 비용을 발생시키는 죽은 무게 [공식]. **초기화는 비용이 0, 컴팩션은 비용이 든다** — 연속성이 필요할 때만 컴팩션.

**L2-2. 선제적 컴팩션 + 지시 동봉** — 포화 직전까지 기다리지 말고 먼저 압축하되, 무엇을 남길지 지시("코드 변경과 테스트 결과만 유지") [공식]

**L2-3. 캐시 히트 유지** — 프리픽스(시스템 지침·초반 컨텍스트)를 고정해 캐시가 유효하도록 유지. 장시간 휴식은 캐시 미스를 만드므로 휴식 전 세션을 정리하거나 캐시 수명 연장 설정을 사용 [공식]

**L2-4. 온디맨드 로드 구조** — 상시 필요한 최소 규칙만 상시 로드하고, 특정 상황에서만 필요한 지침은 호출 시점에 로드되는 구조로 분리:
- 프로젝트 전역 공통 규칙 → 루트 지침 파일 (**200줄 이하 유지** [공식])
- 특정 경로에만 적용 → 경로 스코프 규칙
- 특정 역할에만 필요 → 서브에이전트 정의
- 긴 절차 → 스킬 (호출 시에만 로드 [공식])

**L2-5. 표적 읽기** — 파일 전체가 아니라 필요한 구간만 읽기 [업계]

**L2-6. 전처리 오프로드** — 10,000줄 로그를 모델에 넣는 대신 훅으로 필터링해 수백 토큰만 전달 [공식]

**L2-7. 외부 메모리** — 아키텍처 결정을 파일에 기록해 세션 리셋 후에도 컨텍스트 재구축 없이 복구 (사내 자산: 7-8월 트랙2 M3 "영구 메모리·Stateful 루프")

### 4.3 정량 근거

- 컨텍스트 편집: 100턴 웹검색 평가에서 토큰 소비 **84% 감소**, 동시에 컨텍스트 고갈로 실패했을 워크플로를 완주 [업계]

## 5. 차원 3 — 하네스 엔지니어링

### 5.1 하네스란 무엇인가 (사내 정의 계승)

> **하네스 엔지니어링** — AI 에이전트가 자율적으로 업무를 수행할 수 있도록 **'올바른 환경과 작업장(Harness)'을 설계하고 통제하는** 분야.
> 핵심 철학: *"에이전트를 똑똑하게 만드는 것보다, 에이전트가 오작동하지 않는 환경을 구축하는 것이 더 어렵고 중요하다."*
> 3대 요소: **Context · Constraints · Entropy**
> — 사내 자산 `projects/삼성전자MX_3_Harness/harness_terminology.md`

토큰 관점에서 이 정의를 재해석하면: **하네스는 "한 번의 요청에 무엇이 실려 가는가"를 결정하는 층**입니다. 모델도, 프롬프트도 아닌 그 사이의 배관이 청구서를 정합니다.

### 5.2 낭비 메커니즘

| 메커니즘 | 설명 | 정량 |
|---|---|---|
| **과잉 모델 사용** | 요약·포맷팅·단순 조회 같은 잔일까지 최고성능 모델로 처리 | 라우팅으로 **40~85%** 절감, 품질 **90~95%** 유지 [업계] |
| **도구 스키마 과다 주입** | 연결된 도구의 정의가 매 턴 컨텍스트에 실림 | 도구 서버 3개가 200K 창의 **143K(72%)**를 첫 메시지 전에 점유 [업계] |

### 5.3 레버 (벤더 중립)

**L3-1. 난이도별 모델 라우팅 (= 브레인-실행기 분업)**
- 고난도(복잡한 추론, 아키텍처 결정, 오류 복구) → 상위 모델
- 저난도(요약, 포맷팅, 로그 스캔, 단순 조회) → 경량·고속 모델

> 사내 자산에 이미 존재하며, **고객이 상담에서 직접 언급한 방식과 정확히 일치**합니다:
> "**브레인-실행기 분업 패턴** — 고비용 모델 토큰 낭비를 방지하고 처리 속도를 극대화하는 역할 분담 전략"
> "**마스터-워커 하이브리드** — 단일 초거대 모델 한계(**비용**·무한 루프·컨텍스트 붕괴)와 역할 기반 라우팅 아키텍처"
> — `projects/삼성전자_7-8월교육/제안서/content.json` 트랙1 M1·M3

**삼성 환경 특수성**: 크레딧↔토큰 환산율이 모델마다 다르므로, 라우팅은 단순 단가 차이를 넘어 **환산율 차익**까지 만듭니다. 환산율 표 확보가 이 레버의 정확한 설계 전제입니다 (고객 확인 문항 2번).

**L3-2. 도구 최소화** — 안 쓰는 도구 서버는 비활성화. 도구 정의를 지연 로드하는 방식이 있으면 사용. 동등한 CLI 도구가 있으면 그쪽이 컨텍스트 효율이 좋음 [공식]

**L3-3. 서브에이전트 컨텍스트 격리** — 장황한 작업을 서브에이전트에 위임해 **원문 출력은 서브에이전트 컨텍스트에 남고 요약만 본 대화로 돌아오게** 함 [공식]. 서브에이전트에는 작은 모델 지정 [공식]

**L3-4. 병렬 에이전트 절제** — 팀 규모를 작게, 작업이 끝나면 즉시 종료, 스폰 프롬프트를 짧게 (팀원은 지침 파일·도구·스킬을 자동 로드하므로 스폰 프롬프트의 모든 내용이 시작부터 가중) [공식]

**L3-5. 도구 결과 압축** — 도구 출력을 그대로 넣지 말고 필터링·요약 후 전달 (§4.2 L2-6과 연결)

### 7.1 낭비 메커니즘

| **귀속 불가** | 총량만 보이고 어떤 활동·도구·모델이 소모했는지 분해되지 않음 → 개선할 대상을 특정 못 함 |

### 7.2 레버 (벤더 중립)

**개인 층**

**L5-1. 세션 소모 확인 습관** — 작업 단위로 소모를 확인. 상태 표시줄에 컨텍스트 사용률을 상시 노출 [공식]

**L5-2. 귀속 분석** — 최근 소모를 스킬·서브에이전트·플러그인·도구 서버별 비중으로 분해. **10% 이상을 차지하는 행동(긴 컨텍스트, 캐시 미스 등)에 플래그**가 붙는 방식이 있으면 그대로 진단 도구로 사용 [공식]

**L5-3. 개인 번레이트 기준선** — "내 티어 월 크레딧 ÷ 근무일 = 일 허용 소모". 실제 소모를 이 선과 비교

**조직 층**

**L5-4. 표준 원격측정 수출** — 사용량·비용 지표를 사내 관측 스택으로 스트리밍. 표준 속성(`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`)이 API 호출별로 자동 수집되어 금액·예산 알림으로 환산 가능 [업계]

**L5-5. 사용자·모델별 귀속 대시보드** — 트레이스·사용자·모델·기간별 비용 집계 [업계]. 관리자 콘솔의 지출 리포트·분석 API 활용 [공식]

**L5-6. 티어 배분 정책** — 소모 분포를 근거로 티어를 재배분. 업계 관행상 **미사용 크레딧은 이월되지 않으므로** 과다 배분도 낭비 [업계]

**L5-7. 임계 알림** — 번레이트가 런웨이를 벗어나면 월말 고갈 전에 경고
