Spec & Goal

기초활용심화

Spec · Goal — 착수 전 명세 합의

핵심막연한 요구는 실패합니다. AI가 되물어서 암묵지를 끌어내고, 검증 가능한 인수 기준을 명세로 고정한 뒤 실행합니다.
Spec 주도 개발 (Spec-driven)
  • 구조화된 명세 생성 요구 · 설계안 · 과제 분해 · 인수 기준
  • 명세에 주석 피드백 문서 자체에 의견 달기
  • 선택형 되묻기 AI가 객관식으로 질문해 맥락 추출
  • 제약마다 검증 가능한 케이스 "테스트 가능해야 명세다"
Goal 주도 개발 (Goal-driven)
  • 최종 상태만 기술 경로는 AI가 계획
  • 자율 반복 완료 기준 충족까지 스스로 루프
  • Spec과 통합 Goal이 Spec을 반복 실행·평가
  • 결과 보고 달성 증거와 함께 제출
명세 품질 기준 (공식 케이스)첫 통과율교훈
명세 100줄 이내 · 제약별 테스트 케이스약 95%작고 검증 가능한 명세가 강하다
명세 300줄 이상 (통짜 배짱 명세)약 60%큰 명세는 쪼개서 단계 실행

출처 · docs.qoder.com/user-guide/quest/spec-driven · goal-driven · 공식 고객 사례 — 활용 단계 실습에서 직무 과제의 명세를 직접 작성합니다

트리거 3

문서를 손으로 고치면 동기화 감지

Better Harness — 통제 인프라 진단

핵심"할 수 있다"와 "잘 한다"는 다릅니다. Better Harness는 이해→실행→검증→전달→학습 루프의 끊긴 고리를 찾아 수정 태스크로 바꿔줍니다.

MCP Integration

기초활용심화

MCP — 표준 프로토콜 기반 외부 연동

MCP(Model Context Protocol)는 API·데이터베이스·내부 시스템을 에이전트에 연결하는 표준 방법입니다.

개인·소규모 연동
  • STDIO 전송 로컬 도구·CLI 연동에 적합
  • SSE(HTTP) 전송 원격 호스팅 서버 · 입문자 권장
  • MCP Square 마켓 사전 구성된 서버 원클릭 설치
  • JSON 설정 이름 · 유형 · 엔드포인트 · 명령만 기술
팀·전사 연동
  • 설정 파일을 Git에 공유 모든 팀원이 같은 서버 사용
  • 시크릿은 환경변수로 토큰·비밀은 커밋 금지
  • 엔터프라이즈 허용 목록 관리자가 MCP 서버 허용·차단 (2026.7)
  • 동일 승인 절차 연동 도구도 내장 도구와 같은 규칙
핵심연동의 문제는 기술이 아니라 통제입니다. "누가, 어떤 서버를, 허용했는가"가 문서로 남는 구조가 전사 도입의 전제입니다.

Customization Principle 1

기초활용심화

커스터마이징 원리 ① 파일 기반 구조

핵심Qoder의 서비스화된 기능은 전부 파일로 되어 있고 Git으로 추적됩니다. 잠금 장치가 없다는 것이 커스터마이징의 출발점입니다.
<프로젝트 루트>/
├── AGENTS.md            # 프로젝트 지침 — 팀 공유 (커밋 O)
├── AGENTS.local.md     # 이 기기 전용 지침 (커밋 X)
└── .qoder/
    ├── repowiki/wiki_plan.yaml # Wiki 생성 전략 (Part 3-4에서 심화)
    ├── rules/**/*.md       # 주제별 모듈 규칙 (트리거 지정 가능)
    ├── agents/*.md         # 커스텀 에이전트 (프롬프트 + 설정)
    ├── skills/{이름}/SKILL.md # 재사용 워크플로우
    ├── mcp.json           # 외부 연동 서버 설정
    └── hooks/*.md         # 동작 전/후 강제 장치
가독성
설정이 마크다운·YAML·JSON — 사람이 읽는 텍스트
리뷰 가능
규칙 변경도 PR 리뷰로 통제
⏪ 되돌릴 수 있다
Git 이력 = 커스터마이징 이력

Customization Principle 2

기초활용심화

커스터마이징 원리 ② 적용 범위 3층 · 주입 시점 4종

① 위치의 3층 구조

층위치범위 · 커밋
사용자~/.qoder/내 모든 프로젝트 · 커밋 X
프로젝트<프로젝트>/AGENTS.md해당 프로젝트 팀 공유 · 커밋 O
로컬AGENTS.local.md이 기기 전용 · 커밋 X

② 규칙 트리거 4종 (.qoder/rules)

트리거작동
always_on세션 시작 시 항상 주입
manual자동 주입 없음 — 명시 호출만
model_decision경로+설명만 주입, 필요 시 AI가 읽음

핵심규칙 설계의 본질은 내용만이 아니라 "언제 주입되는가"를 설계하는 것입니다. 항상 주입하면 컨텍스트가 낭비되고, 조건 주입이야말로 숙련도의 차이입니다.
실습심화 단계 실습 ① — 팀 컨벤션 3개를 always_on 규칙 1개 + glob 규칙 2개로 분리 작성 · 로컬 전용 예외 1개를 AGENTS.local.md로 분리

Customization Principle 3

기초활용심화

커스터마이징 원리 ③ Wiki 사전 지시와 수정 보호

  documents:  # 페이지 목록을 주면 이 목록대로만 생성 (엄격 모드)
    - title: "시스템 구조 개요" goal: "핵심 모듈과 상호작용 설명"
    - title: "주문 시스템" parent: "시스템 구조 개요"
knowledgecard:
  notes: - text: "결제·주문 핵심 서브시스템 중심으로"
scope:
  include: ["src/**"] exclude: ["**/test/**"]  # .gitignore 문법

wiki_plan.yaml로 방향 설정
2
생성
지정 문서 구조대로 산출

사람이 수정
/knowledge 명령으로 보완
4
수정 보호

종합 실습 — 팀 프로젝트 6단계 셋업

기초·활용·심화에서 배운 것을 하나의 흐름으로 완성합니다. 6단계 전체가 "우리 팀의 Qoder 프로젝트"가 됩니다.

STEP 4
Wiki 생성·검토
생성 → /knowledge 수정 → 보호 확인
STEP 5
커밋 · 팀 공유
.qoder/ 포함 push → 팀원 pull 실습
STEP 6
Better Harness
진단 → 수정 1건 → 재진단 점수 확인

평가 · 6단계 체크리스트 실행 완료 + 팀원 1인의 pull&실행 확인으로 수료 판정 (지마켓 발표덱 S31 "검증 장치" 방식과 동일)
