# 프롬프트 엔지니어링

Google, OpenAI, Microsoft 등의 논문과 **"Principled Instructions Are All You Need"** (LLM 성능 향상을 위한 26가지 원칙) 등 연구 결과에 근거 

### 1. 페르소나(Persona) 정의: "누구"의 관점인가?

AI에게 역할을 부여하면 답변의 관점, 판단 기준, 어조를 좁혀 결과의 일관성을 높일 수 있다. 단, Claude Code에서는 역할만 주지 말고 `역할 + 작업 목표 + 현재 코드 맥락 + 완료 기준`을 함께 줘야 한다.

모델 알고리즘 관점에선 기존의 context를 통해 관련 도메인의 언어 영역을 활성화한다.

Claude Code의 `CLAUDE.md`도 강제 설정이 아니라 컨텍스트로 읽히므로, 짧고 구체적인 지시가 더 안정적이다. ([Claude API Docs](https://docs.anthropic.com/en/docs/claude-code/memory?utm_source=chatgpt.com))

### GOOD

```markdown
너는 10년차 프론트엔드 아키텍트다. 
현재 프로젝트를 읽고 index.html의 UI/접근성/반응형 문제를 리뷰하라. 
바로 수정하지 말고 
먼저 문제 목록, 근거 파일, 개선 우선순위, 테스트 기준을 두괄식으로 제시하라.
```

### BAD

```markdown
내가 첨부한 index.html를 프론트엔드 엔지니어처럼 봐줘.
특히 UI 등이 구조적으로 괜찮은지 확인 후, 개선점을 도출해.
```

### 2. 조건부 확률에 근거한 생성형 모델(파운데이션 모델 - gpt, gemini 등)은 원샷/퓨샷 프롬프팅 (One-Shot/Few-Shot Prompting): "예시"가 답변 효율을 압도적으로 증진시킨다. - In Context Learning

GPT-3 논문에서 강조된 개념으로, 아무런 예시 없이 질문하는 것(Zero-Shot)보다 **1~3개의 예시(Shot)를 주었을 때** 정확도가 비약적으로 상승함을 관찰. 업무 형식을 맞출 때 가장 강력하며 효과적인 도구

모델에게 말로 설명하는 대신, **원하는 결과물의 패턴을 예시로 보여주는 방식**이다. 

`리뷰 방식`, `출력 형식`, `수정 전 확인 절차`, `테스트 기준`까지 예시로 보여주는 게 좋다.

### GOOD

```
너는 10년차 프론트엔드 아키텍트이자 접근성 리뷰어다.

현재 프로젝트의 `index.html`만 먼저 읽고, UI 구조 / 접근성 / 반응형 / 유지보수성 관점에서 문제를 진단하라.
아직 파일을 수정하지 마라. 추측으로 말하지 말고, 반드시 실제 코드 구조나 선택자/섹션명을 근거로 들어라.

출력은 아래 형식으로 고정하라.

1. 전체 판정
- 현재 페이지가 강의 시연용 HTML로 충분한지 / 부족한지 한 문단으로 판단

2. 문제 목록
- [심각도: High/Medium/Low]
- 문제:
- 근거:
- 왜 문제인지:
- 수정 방향:

3. 개선 우선순위
- 1순위:
- 2순위:
- 3순위:

4. 수정 전 테스트 기준
- 데스크톱 1440px:
- 태블릿 768px:
- 모바일 375px:
- 키보드 탐색:
- 스크린리더/시맨틱 태그:
```

### BAD

```
index.html 좀 봐줘.
프론트엔드 전문가처럼 UI랑 반응형 괜찮은지 확인해줘.
문제 있으면 알아서 고쳐줘.
```

### 3. 생각의 사슬 (Chain of Thought, CoT): "과정"을 유도하라

Google Research 팀이 발표한 핵심 개념. AI에게 답을 바로 요구하지 말고, **"단계별로 생각하라(Let's think step by step)"**고 지시하면 복잡한 추론이나 논리적 업무의 정답률이 크게 상승.

- **WHY?**
    - AI가 답변을 생성하면서 스스로 논리적 단계를 밟아가게 하여 '할루시네이션(거짓 정보 생성)'을 줄이도록 동작한다.
- **적용 예시 (기획안 검토):**
    
    > "이 기획안이 현실적인지 판단해줘." (X)
    > 
    > 
    > "이 기획안의 실현 가능성을 다음 단계별로 분석하라. 1. 예산 측면, 2. 일정 측면, 3. 인력 측면으로 나누어 생각한 뒤 결론을 확정하라." (O)
    > 

### 4. 청중 설정 (Audience Persona)

답변을 읽을 대상을 명확히 하면, AI가 어조와 난이도를 자동 조절. 결과물의 '수준'을 명시

- **적용 예시:**
    
    > "아래에 첨부한 내 프로젝트를 개발자가 아닌, 비개발자 투자자들에게 쉽고 상세하게 설명하는 발표자료를 만들고 싶어. 파이프라인을 설명할 때, 어려운 개발 언어를 직관적으로 이해할 수 있도록 표/그림/예시를 포함한 발표자료를 만들어라."
    > 

### 5. "출력 결과에 예시를 포함하도록 요청하라" (Showcases)

단순한 설명보다 구체적인 사용 사례를 함께 요구하면 AI 정확도가 올라간다. 

- **핵심:** 결과 생성물에 **예시**를 같이 생성하도록 지시
- **실무 적용:** "내 프로젝트에 개인화 달성을 위해 A 기법을 적용시키고 싶다. 설계도를 아이디어 구상-의심/비판-운영 리스크 전수조사-확정 순으로 단계적으로 구상 완성하고, A 기법이 실제로 구현되었을 때, 유저들의 사용 시나리오를 3가지 생성하라.”

### 6. "결과물을 받기 전, 질문을 통해 정보를 보충하게 하라" (Reverse Questioning)

프롬프트가 부족할 때, AI가 추측해서 답변하게 두지 말고, 추측/추론 사항에 대해 질문하도록 지시하라.

- **핵심:** AI는 미결정 사항에 대해 추론을 진행한다. 사용자가 놓친 사항들에 대해 직접적인 질문을 지시
- **실무 적용:** "이 기획안을 보강하고 싶은데, 네가 더 좋은 답변을 내놓기 위해 **나한테 더 알아야 할 정보가 있다면, 이에 대한 질문 3개만 해라.**"

### 7. "구체적인 제약 사항 추가" (Constraint Specification)

AI는 자유도가 높을수록 정확도가 떨어진다. 적절한 제약을 주면 더 깊고 실용적인 답변이 나온다. 

- **핵심:** 단어 수, 특정 단어 포함 여부, 대상 등을 엄격히 지정
- **실무 적용:** "**초등학생 저학년이 이해할 수 있는 맥락 수준 & 쉬운 단어를 활용하여** 200자 이내로 작성하라."

### 8. "출력물의 구조를 먼저 정의하라" (Output Structure)

AI가 글을 쓰기 시작하기 전에 어떤 구조로 쓸지 정해주면 논리적 흐름이 깨지지 않고 결과물 수준이 상승

- **핵심:** "표 형식으로", "글머리 기호를 사용해서" 등 형식을 예시로 지정
- **실무 적용:** "답변은 반드시 `1. 개요 - 2. 문제점 - 3. 해결책 - 4. 기대효과` 순서로 작성하라"

### 9. 반복과 강조 (Repetition & Emphasis)

중요한 명령은 프롬프트의 끝부분 등에 한 번 더 강조하는 것이 효율적

- **핵심:** 핵심 지시 사항을 프롬프트 마지막에 다시 언급
- **실무 적용:** "(앞에서 길게 설명한 뒤) **기억해라: 반드시 AI PhD 수준의 깊이 있는 분석이어야 한다.**"

## 10. 프롬프트 경계 분리: XML / Markdown Delimiter

긴 프롬프트에서 `지시사항`, `참고자료`, `예시`, `입력`, `출력형식`을 섞어 쓰면 모델이 어디까지가 규칙이고 어디부터가 데이터인지 헷갈린다. Anthropic은 Claude 프롬프트에서 XML 태그가 복잡한 프롬프트를 명확히 파싱하는 데 도움 된다고 설명하고, OpenAI도 Markdown/XML이 논리적 경계를 나누는 데 유용하다고 설명한다.

### GOOD

```
<role>
너는 10년차 프론트엔드 아키텍트이자 접근성 리뷰어다.
</role>

<context>
현재 프로젝트에는 단일 index.html 파일이 있으며, 강의 시연용 웹페이지 품질을 평가해야 한다.
</context>

<task>
index.html을 읽고 UI 구조, 접근성, 반응형, 유지보수성 문제를 진단하라.
아직 파일을 수정하지 마라.
</task>

<output_format>
1. 전체 판정
2. 문제 목록
3. 근거 파일/선택자
4. 개선 우선순위
5. 테스트 기준
</output_format>
```

## 11. Grounding / 근거 기반 답변 강제

**품질 증진에는 실제 파일·라인·선택자·테스트 결과에 근거한 답변 및 작업이** 중요하다. Anthropic은 긴 문서 작업에서 관련 인용/근거를 먼저 뽑게 하면 노이즈를 줄이는 데 도움이 된다고 설명하고, Microsoft도 LLM 응답은 검증이 필요하며 grounding을 통해 정확성을 높여야 한다고 설명한다.

### GOOD

```
현재 프로젝트를 분석하라.
모든 판단은 반드시 실제 파일명, 코드 구조, 선택자명, 함수명, 테스트 결과 중 하나를 근거로 제시하라.
근거 없이 "좋아 보인다", "개선 가능하다", "일반적으로" 같은 표현으로 판단하지 마라.
```

## 12. Tool-use Policy: 언제 읽고, 언제 수정하고, 언제 테스트할지 명시

CLI 기반에서는 파일 읽기, 수정, 테스트 실행을 할 수 있는 작업자라서, **수정 전 리뷰인지 / 바로 구현인지 / 테스트까지 돌릴지**를 명시해야 한다. Anthropic은 “제안만 할지, 실제 구현할지”를 명확히 지시해야 하며, 불명확하면 모델이 제안에 머물거나 반대로 너무 빨리 구현할 수 있다고 설명한다.

### GOOD

```
먼저 파일을 읽고 문제를 진단하라.
1차 응답에서는 절대 파일을 수정하지 마라.
내가 "수정 진행"이라고 말한 뒤에만 index.html을 수정하고, 수정 후에는 브라우저 기준 테스트 항목을 체크하라.
```

## 13. 작업 분해 / Least-to-Most Prompting

복잡한 작업은 한 번에 “완성해”라고 주면 모델이 설계·구현·검증을 섞어서 망가뜨릴 수 있다. Least-to-Most prompting은 복잡한 문제를 쉬운 하위 문제로 분해한 뒤 순차적으로 해결하게 하는 방식이며, 논문에서도 복잡한 추론을 subproblem으로 나눠 해결하는 접근으로 제안됐다.

### GOOD

```
이 작업을 한 번에 구현하지 마라.

먼저 다음 순서로 나눠서 진행하라.
1. 현재 index.html 구조 파악
2. UI/접근성/반응형 문제 분류
3. 수정 계획 작성
4. 수정 전 테스트 기준 정의
5. 내가 승인하면 구현
6. 구현 후 테스트 결과 요약
```

## 14. Self-Check / 검증 루브릭 강제

모델이 답을 낸 뒤 스스로 기준표에 맞춰 검증하게 해야 한다. Anthropic은 코딩·수학 작업에서 완료 전 테스트 기준에 대해 답을 검증하게 하는 것이 오류를 잡는 데 도움이 된다고 설명한다. Self-Consistency 논문도 하나의 추론 경로만 쓰지 않고 여러 경로의 일관된 답을 선택하는 방식이 복잡한 reasoning 성능을 높인다고 제안한다.

### GOOD

```
최종 답변 전에 아래 기준으로 자기 검증하라.

- 실제 파일을 근거로 판단했는가?
- 수정하지 말라는 지시를 지켰는가?
- UI, 접근성, 반응형을 모두 분리해서 봤는가?
- 각 문제에 우선순위와 테스트 기준이 있는가?

위 기준 중 하나라도 빠졌다면 최종 답변 전에 보완하라.
```

## 15. State / Context 관리 지시

CLI 기반 프로젝트에서는 장시간 작업이 많기 때문에 “현재 어디까지 했는지”를 파일이나 체크리스트로 남기게 해야 한다. Anthropic은 장기 작업에서 진행 상태, 테스트 결과, 작업 상태를 JSON이나 progress note로 관리하는 방식을 권장하며, 새 컨텍스트에서도 `progress.txt`, `tests.json`, git log 등을 읽고 이어가게 할 수 있다고 설명한다.

### GOOD

```
작업이 길어질 경우 `progress.md`를 만들어 현재 상태를 기록하라.

기록 항목:
- 완료한 작업
- 수정한 파일
- 남은 작업
- 실패한 테스트
- 다음 세션에서 먼저 읽어야 할 파일

새 작업을 시작할 때는 먼저 `progress.md`와 git status를 확인하라.
```

## 16. 일반해 금지 / 테스트 통과용 하드코딩 방지

Claude Code는 테스트를 통과시키기 위해 특정 케이스만 맞추는 우회 구현을 할 수 있으므로, “테스트 통과”가 아니라 “일반적으로 맞는 로직”을 요구해야 한다. Anthropic도 테스트 케이스에만 맞춘 하드코딩이나 workaround를 피하고, 모든 유효 입력에 맞는 일반 목적 솔루션을 구현하라고 지시하는 패턴을 제시한다.

### GOOD

```
테스트를 통과시키기 위한 하드코딩을 하지 마라.
특정 화면 크기, 특정 텍스트, 특정 카드 개수에만 맞는 임시 CSS를 만들지 마라.
모든 유효한 카드 개수와 일반적인 화면 크기에서 유지되는 구조적 해결책을 구현하라.
```

## 17. 다중 후보 생성 후 선택: Self-Consistency / Tree-of-Thoughts 계열

복잡한 설계, 기획, 아키텍처 판단은 하나의 답만 바로 뽑게 하지 말고 **여러 후보를 만들고 비교 후 선택**하게 해야 한다. Tree of Thoughts는 여러 reasoning path를 탐색·평가·백트래킹하는 방식이 필요한 문제에서 효과적이라고 설명하며, Self-Consistency도 여러 reasoning path 중 일관된 답을 선택하는 전략을 제안한다.

### GOOD

```
바로 하나의 개선안을 확정하지 마라.
```

## 18. 불확실성 / Fallback Policy 명시

이건 Reverse Questioning과 달리, 작업 도중 해결책이나, **정보가 없을 때 등 모델이 어떻게 행동해야 하는지 정책을 정하는 것**이다. Microsoft는 system message 설계에서 모델이 정보 부족, 범위 밖 요청, 애매한 요청을 만났을 때의 fallback behavior를 명시하라고 권장한다.

### GOOD

```
정보가 부족하면 추측하지 마라.

정책:
- 파일에서 확인 가능한 내용은 근거와 함께 말한다.
- 파일에서 확인 불가능한 내용은 "확인 불가"라고 표시한다.
- 판단에 필요한 정보가 3개 이하라면 질문한다.
- 3개를 초과하면 합리적 가정을 명시하고 임시안을 제시한다.
```
