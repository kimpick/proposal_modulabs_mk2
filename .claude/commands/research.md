# /research — 도메인 조사 → context.md (mk2)

신규(또는 정보 부족) 고객사의 조사를 모아 `projects/<기업명>/context.md`를 만들고,
회차가 바뀌어도 유지될 장기 기억은 `memory/clients/<기업명>.md`에 적재한다.
`$ARGUMENTS` = 기업명.

## 원칙 — 조건부(라우팅)로 최소 작업
> **이미 아는 고객사면 외부 웹 리서치를 생략/축소한다.**
> - `memory/clients/<기업명>.md`가 있고 최근(updated) 정보가 충분 → **사내 확인만**, 외부 웹은 생략(또는 "최근 뉴스"만).
> - 신규·미지 고객사 → 사내 + 외부 웹 풀 리서치.
> 회사 개요를 두 곳에서 중복 생산하지 않는다: **사내 정보가 1차, 외부는 사내에 없는 것만 보강.**

> DB 스키마·데이터소스 URL·컬럼 옵션은 `docs/notion_db_스키마_캐시.md` 에 캐시돼 있다.
> 스키마를 `fetch` 하기 전에 그 문서를 먼저 볼 것 (fetch 1회당 약 7,000 토큰).

## STEP 0. 기존 리서치 문서 존재 확인 (가장 먼저 · 절감 효과 최대)
> **이미 누군가 조사해 둔 문서가 있으면 새로 조사하지 않는다.**

1. Notion `[비즈] 영업/제안현황`의 해당 고객사 페이지 하위 `업무 관리` DB를 먼저 검색한다.
   `기관 리서치`·`1차 유선 상담`·`메일 문의` 같은 항목이 이미 있으면 **그걸 `context.md`로 이관**하고 STEP 3(외부 웹 리서치)을 건너뛴다. (STEP 2 확인 사항 정리는 건너뛰지 않는다 — 문의 원문 자체를 다시 보는 것이라 이미 리서치가 있어도 필요하다.)
2. `projects/` 안에 같은 고객사의 과거 폴더가 있는지 확인한다(사명 변경·표기 차이 주의).

서울신용보증재단 건이 이 경우였다. 완성된 `기관 리서치` 리포트가 Notion에 있어 외부 웹 리서치를 **0회**로 끝냈다.

## STEP 1. 사내 정보 (1차 소스)
- `memory/clients/_INDEX.md`에서 폴더↔고객사 매핑 확인 → 관련 `projects/<폴더>/`의 `요구조건.md`·`MEMORY.md`·회의록 확인.
- (연동돼 있으면) Gmail·Notion에서 최초 문의·미팅로그·상업조건을 원문 근거와 함께 수집.
- **Slack은 `modulabs.slack.com`(커뮤니티 워크스페이스)만 참고 가능.** 실제 회사 업무공간인 `modulabsworks.slack.com`은 보안상 읽기 권한을 주지 않기로 결정(2026-09-10) — 검색 시도하지 말 것. 인바운드 문의 원문 자체는 Zapier가 Notion 과업 페이지 본문(`☎️ [기초 상담 요청 정보]` callout)에 이미 옮겨두므로 지장 없음.
- 확인된 사실만. 없는 건 `(미확인)`.

### Notion DB 조회는 SQL 우선
Notion DB에서 목록·후보를 찾을 때는 **`query-data-sources`의 SQL 모드**로 필요한 컬럼만 집계한다.
행을 훑기 위해 페이지를 하나씩 `fetch`하지 않는다.

| 방식 | 실측 비용 |
|---|---|
| SQL 집계·필터 1회 | 약 300 토큰 |
| 페이지 1건 `fetch` | 약 5,000 토큰 (S3 서명 URL·빈 블록 노이즈 포함) |
| DB 스키마 `fetch` 1회 | 약 7,000 토큰 (select 옵션 URL까지 전부) |

강사DB에서 후보 13명을 SQL 4회(약 1,200 토큰)로 추렸다. 같은 일을 페이지 fetch로 하면 13 × 5,000 = 65,000 토큰이었다.
**페이지 `fetch`는 최종 선택된 대상에만 쓴다.**

개인정보(연락처·이메일·주소)는 산출물에 쓸 수 없으므로 **`SELECT` 목록에서 아예 제외**한다.

## STEP 2. 고객사에 확인해야 할 사항 정리 (모든 건 필수 — 생략 불가)
> **초기 상담 문의는 커리큘럼 설계·견적·고객 응대에 필요한 정보가 항상 부족하다.**
> 예: "온라인 교육"이라고만 적혀 있으면 LMS 제공을 원하는지 녹화 영상을 원하는지 알 수 없고,
> 희망 주제가 3개면 그걸 순차로 다 다루는 건지·트랙을 나눠 병렬로 하는 건지·제안서를 보고 하나만 고를 건지 알 수 없다.
> 이런 공백을 방치하면 커리큘럼을 잘못된 전제로 설계하게 된다. 문의 원문을 검토해
> 애매하거나 빠진 정보를 찾아 체크리스트로 정리한다 — **이 목록이 PM의 1차 유선 상담 질문지가 된다.**

아래 항목을 문의 원문과 하나씩 대조한다. **확인된 것도 확인 안 된 것도 전부 기록**한다
(이미 확인된 항목까지 적어야 PM이 "이건 다시 안 물어봐도 되는구나"를 알 수 있다).

| 확인 항목 | 왜 필요한가 |
|---|---|
| 온라인 교육 형태 | LMS 제공 / 녹화 영상 / 실시간 화상 중 무엇인지에 따라 만들어야 할 산출물이 달라짐 |
| 복수 주제·과정 처리 방식 | 순차로 전부 다루는지 / 트랙 병렬 진행인지 / 제안서 보고 택1인지 — 시간 배분·트랙 설계에 직결 |
| 일정 확정 정도 | 희망 시작일·총 회차·회당 시간이 확정인지 협의 가능인지 |
| 예산 | "미정"이어도 대략적 상한선·과거 유사 사례가 있는지(견적 설계 방향을 잡는 데 필요) |
| 장소·인프라 제약 | 오프라인 시 지역(강사 이동 가능 범위), 사내망 보안 정책상 특정 AI 툴 사용 제한 여부 |
| 대상자 상세 | 인원이 범위(예: 10~30)면 확정 시점, 직군·연차·AI 활용 사전 수준 |
| 의사결정 구조 | 문의 담당자가 예산 승인권자인지, 최종 확정까지 거칠 절차가 있는지 |

> 이 표는 출발점이다. 문의 내용에 따라 위 항목 외에 커리큘럼 설계·견적에 꼭 필요한데 빠진 정보가 보이면 추가한다.

`context.md`에는 아래 형식으로 넣는다:

```markdown
## PM 확인 필요 사항 (1차 유선 상담용)
| 항목 | 문의에서 확인된 내용 | 비고 |
|---|---|---|
| 온라인 교육 형태 | (미확인) | LMS/녹화영상/실시간 중 확인 필요 |
| 복수 주제 처리 방식 | (미확인) | 3개 주제 순차/병렬/택1 여부 확인 필요 |
| 예산 | 미정 / 사내 협의 중 | 대략적 상한선이라도 확인 시도 |
...
```

## STEP 3. 외부 웹 리서치 (조건부 — 신규·미지일 때만)
- 기업 개요·AI 도입 현황·조직/채용·최근 뉴스·경쟁사 동향. 회사 기본은 사내에 있으면 재조사 금지.
- 불확실은 `[추정]`/`[미확인]`, 출처(공식 홈페이지 필수)를 단다.

> **토큰 절감 — 서브에이전트 격리 + 출력 상한.**
> 이 단계는 서브에이전트로 돌려 **요약만** 받는다(원문·검색결과를 메인 컨텍스트에 쌓지 않음).
> 상한을 정하지 않으면 요약이 원문만큼 길어지므로, 지시에 **섹션당 글자 수 상한**을 명시한다.
> 권장: 6섹션(개요·AI 도입 현황·조직·전략 방향·업계 동향·제안 논리) × 각 800자 이내 + 출처 URL 목록.
> 이렇게 하면 외부 리서치가 메인 컨텍스트에 유입되는 양이 약 5,000 토큰으로 고정된다.

## STEP 4. context.md 작성 (제안 설계 입력)
`projects/<기업명>/context.md`에 아래를 채운다(제안 타입·대상·목표·제약의 근거):
- 교육 대상/직군, 인원, 목표, 형태(온·오프/사내망), 인프라·보안 제약, 사용 도구 수준
- 확정 요구사항·일정·장소(있으면), 미정은 `[협의 필요]`
- 도메인 특이사항(업종·최근 이슈)과 그것이 커리큘럼에 주는 함의
- **STEP 2에서 만든 "PM 확인 필요 사항" 표** (빠뜨리지 말 것 — 이번 리서치 고도화의 핵심 산출물)

## STEP 5. 장기 기억 갱신 (memory/clients)
- `memory/clients/<기업명>.md`가 없으면 `memory/clients/_TEMPLATE.md`를 복사해 생성, `_INDEX.md`에 매핑 추가.
- 회차가 바뀌어도 유지될 것만(담당자 성향·확정 조건·통한 것/거절 사유·선호 포맷). 이번 회차 경과는 `projects/<폴더>/MEMORY.md`.
- 모든 항목에 `[출처: 파일 또는 날짜]`. 확정 금액·계약은 Notion 「영업/제안현황」이 원본(여기엔 흐름만).

## 산출
- `projects/<기업명>/context.md` (다음 단계 `/propose`의 입력)
- `memory/clients/<기업명>.md` (신규/갱신)

→ 다음: `/propose <기업명>` 으로 content.json 작성·검토·빌드.
