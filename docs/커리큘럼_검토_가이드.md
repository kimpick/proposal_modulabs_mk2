# 커리큘럼 다차원 검토 가이드

## 개요

`/review` 명령어 실행 시 4명의 전문 검토 에이전트가 병렬로 `content.json`을 다차원으로 검토합니다. 각 에이전트는 독립적인 관점에서 판정 기준에 따라 통과/수정 필요 여부를 결정합니다.

## 문서 역할 분리

리뷰 체계는 사용자가 판단해야 하는 문서와 Codex가 자동으로 작성/활용하는 문서를 분리합니다.

| 구분 | 문서/파일 | 역할 |
|---|---|---|
| 사용자 의사결정 | `docs/review_governance.md` | WARN 허용 여부, 최신성 검색 허용, 도구 범위 변경 등 사업적 판단 기록 |
| Codex 자동 실행 | `docs/review_agent_prompts.md` | 4개 리뷰어의 공통 출력 형식과 관점별 프롬프트 |
| 로컬 자동 검증 | `scripts/validate_content.py` | API 비용 없이 스키마, 도구 일관성, HTML, PDF 가독성 위험을 사전 점검 |

Codex는 `docs/review_governance.md`를 자동으로 덮어쓰지 않습니다. 의사결정 기록은 사용자가 명시적으로 요청한 경우에만 수정합니다.

## 검토 에이전트 구성

### ① 커리큘럼 흐름 검토 (Flow Reviewer)

**역할**: 커리큘럼의 논리적 흐름, 난이도 진행, 시간 배분의 합리성을 검토합니다.

| # | 항목 | 판정 기준 | 심각도 |
|---|---|---|---|
| 1 | 모듈 순서 | 기초→심화로 자연스럽게 진행하는지 (트렌드→비교→심화→실습→통합 순이 이상적) | ⚠️ WARN |
| 2 | 시간 배분 | 0.5H 모듈은 실습 없으면 너무 짧은지, 2H 모듈은 적절한지 | ⚠️ WARN |
| 3 | 선행 학습 | 뒤 모듈에서 처음 나오는 개념이 이전에 소개되었는지 | ❌ FIX |
| 4 | 트랙 간 균형 | 기초반/심화반 분량과 난이도 차이가 명확한지 | ⚠️ WARN |
| 5 | 산출물 수렴 | intro 목표 → 모듈 활동 → output 산출물이 논리적으로 연결되는지 | ❌ FIX |
| 6 | 중복 모듈 | 기초반/심화반에 같은 주제가 있으면 차별성이 충분한지 | ⚠️ WARN |
| 7 | 실습 비중 | 총 시간 대비 실습(또는 체험) 비율이 50% 이상인지 | ⚠️ WARN |
| 8 | 커리큘럼 타이틀 | curriculum_title이 내용을 잘 대변하는지 | 💡 INFO |

---

### ② 최신성 검토 (Recency Reviewer)

**역할**: AI 도구, 기술 트렌드, 버전 정보의 현재 정확성을 2026년 기준으로 검토합니다.

| # | 항목 | 판정 기준 | 심각도 |
|---|---|---|---|
| 1 | AI 도구 현재성 | 명시된 도구들이 2026년 현재 서비스 중인지 | ❌ FIX |
| 2 | 트렌드 키워드 정확성 | Harness Engineering, Agentic AI, Vibe Coding 등이 맥락에 맞게 사용되었는지 | ⚠️ WARN |
| 3 | 모델 버전 정확성 | Gemini 3, Gemma 4, ChatGPT 버전 등 구체적 명칭이 사실인지 | ❌ FIX |
| 4 | 무료 체험 가능성 | "무료 체험" 안내 도구가 실제 무료/프리미엄 트라이얼인지 | ⚠️ WARN |
| 5 | 기술 용어 정확성 | RAG, 프롬프트 엔지니어링, 양자화, 경량화 등 용어 사용이 정확한지 | ❌ FIX |
| 6 | 최신 대안 | 더 적합한 무료 도구가 있는지 (예: Perplexity 대신 비슷한 도구) | 💡 INFO |
| 7 | on-device/엣지 AI | Gemma, Phi 등 경량 모델 최신 동향 반영 여부 | 💡 INFO |

---

### ③ 어투·양식 검토 (Tone & Format Reviewer)

**역할**: 대상에 맞는 톤, 문서 포맷 일관성, 도구 명시의 3-way 체크를 검토합니다.

| # | 항목 | 판정 기준 | 심각도 |
|---|---|---|---|
| 1 | 대상 맞춤 톤 | 시니어면 "맛보기/체험" 가벼운 톤, 실무자면 "활용/적용" 실전 톤 | ⚠️ WARN |
| 2 | 대학 vs 기업 구분 | "비개발자", "실무" 표현은 기업에만 사용 (CLAUDE.md 규칙) | ❌ FIX |
| 3 | 모듈 포맷 일관성 | 모든 모듈이 `<b>키워드</b> — 설명` 패턴을 따르는지 | ❌ FIX |
| 4 | **도구 일관성 (3-way check)** | `tech_stack` = 모든 `tracks[].tools`의 합집합 | ❌ FIX |
| 5 | 도구 누락 체크 | `tracks[].tools`에 없는 도구가 `items`에 나오면 ❌ | ❌ FIX |
| 6 | 도구 불필요 체크 | `tech_stack`에 있는데 어느 track에도 없으면 ⚠️ | ⚠️ WARN |
| 7 | 제목 품질 | module_name이 서술형 명사구인지, track_name이 직관적인지 | ⚠️ WARN |
| 8 | HTML 태그 안전성 | `<b>`, `<ul>`, `<li>` 등이 올바르게 닫혔는지 | ❌ FIX |
| 9 | 공백/오타 | 후행 공백, 중복 단어, 맞춤법 검사 | 💡 INFO |
| 10 | info 필드 포맷 | keyword의 `\n`이 PDF에서 의도대로 보이는지 | ⚠️ WARN |
| 11 | subtitle 품질 | 한 줄 요약이 실제 내용을 잘 대변하는지 | ⚠️ WARN |

---

### ④ PDF 가독성 검토 (Readability Reviewer)

**역할**: PDF 렌더링 시 발생할 수 있는 가독성 문제, 페이지 분할, 템플릿 매핑을 검토합니다.

| # | 항목 | 판정 기준 | 심각도 |
|---|---|---|---|
| 1 | 텍스트 오버플로우 | items 개별 항목이 100자 이상이면 PDF에서 줄바꿈 이슈 | ⚠️ WARN |
| 2 | 모듈당 item 수 | 5개 이상이면 모듈 박스가 너무 높아짐 | ⚠️ WARN |
| 3 | schedule_message HTML | 테이블 태그, 인라인 스타일이 Edge headless에서 렌더링되는지 | ❌ FIX |
| 4 | 트랙 분할 | 트랙이 여러 개일 때 page-break가 자연스러운지 | ⚠️ WARN |
| 5 | intro/design_framework 길이 | content-box가 A4 한 페이지 초과하면 분할 위험 | ⚠️ WARN |
| 6 | 한글 폰트 | Pretendard CDN이 오프라인 PDF에서 fallback 되는지 | 💡 INFO |
| 7 | 모듈명 길이 | module-name이 130px 왼쪽 컬럼에서 안 잘리는지 (15자 이내 권장) | ⚠️ WARN |
| 8 | 템플릿 매핑 | content.json 키가 실제 템플릿(track.html 등)에 존재하는 필드인지 | ❌ FIX |

## 검토 결과 리포트 형식

각 리뷰어는 `docs/review_agent_prompts.md`의 JSON 형식을 우선 사용합니다. 사용자에게 공유할 때는 다음 구조화된 마크다운 형식으로 요약합니다:

```markdown
## [리뷰어명] 검토 결과

### 판정 요약
- ✅ PASS / ⚠️ PASS_WITH_NOTES / ❌ NEEDS_FIX

### 검토 항목
| # | 항목 | 판정 | 설명 |
|---|---|---|---|
| 1 | [항목명] | [판정] | [상세 설명] |
```

---

## 판정 기준

| 기호 | 의미 | 설명 |
|---|---|---|
| ❌ FIX | CRITICAL | 반드시 수정해야 할 치명적 문제 |
| ⚠️ WARN | 권장 수정 | 수정 권장 사항 (결정권자에 따라 판단) |
| 💡 INFO | 참고 사항 | 개선 제안 (수정 필수 아님) |
| ✅ PASS | 통과 | 문제 없음 |

---

## 종합 판정 규칙

4명의 리뷰어 결과를 취합하여 최종 판정을 도출합니다.

| 조건 | 판정 | 다음 액션 |
|---|---|---|
| FIX 1개 이상 | ❌ NEEDS_FIX | 사용자 수정 후 재검토 |
| WARN 3개 이상 | ❌ NEEDS_FIX | 사용자 확인 후 수정 권장 |
| WARN 1-2개 | ⚠️ PASS_WITH_NOTES | `/build` 진행 가능 (참고 사항 확인) |
| WARN 0개 | ✅ PASS | 즉시 `/build` 진행 |

---

## 검토 워크플로우

```
/review {기업명}
  ↓
scripts/validate_content.py로 로컬 deterministic 검증
  ↓
4명의 에이전트가 content.json 병렬로 검토
  ↓
각 에이전트가 개별 판정 출력
  ↓
종합 판정 도출
  ↓
FIX/WARN의 영향과 수정 선택지 제시
  ↓
사용자에게 결과 공유
  ↓
NEEDS_FIX → 사용자 수정 → /review 재실행 또는 /build
PASS_WITH_NOTES → /build 진행 가능
PASS → 즉시 /build 진행
```

### 로컬 검증 명령

```bash
PYTHONIOENCODING=utf-8 python scripts/validate_content.py {기업명}
PYTHONIOENCODING=utf-8 python scripts/validate_content.py {기업명}/{제안서폴더}
PYTHONIOENCODING=utf-8 python scripts/validate_content.py projects/{기업명}/{제안서폴더}/content.json
```

로컬 검증은 LLM이나 외부 API를 호출하지 않습니다. 따라서 비용 없이 매번 실행할 수 있습니다.

## 실행 예시

```bash
/review 삼성전자
```

**출력 예시**:

```
[Flow Reviewer] ✓ 검토 완료
[Recency Reviewer] ✓ 검토 완료
[Tone & Format Reviewer] ✓ 검토 완료
[Readability Reviewer] ✓ 검토 완료

=== 종합 판정 ===
⚠️ PASS_WITH_NOTES

WARN 2개:
1. [Flow Reviewer] #2 시간 배분: 0.5H 모듈 "AI 트렌드 개요"에 실습이 없어 너무 짧음
2. [Tone & Format Reviewer] #7 제목 품질: module_name "AI 도입 전략"이 구체적이지 않음

INFO 3개:
1. [Recency Reviewer] #6 최신 대안: Perplexity 대신 더 최신 도구 고려 가능
2. [Readability Reviewer] #6 한글 폰트: 오프라인 PDF에서 fallback 확인 필요
3. [Flow Reviewer] #8 커리큘럼 타이틀: "직무별 맞춤형 교육"으로 수정 권장

💡 건의사항:
- 0.5H 모듈을 1H로 확장하고 실습 추가 검토
- module_name을 "AI 도입 전략 수립"으로 구체화
- /build로 진행 가능하지만 위 사항 확인 후 빌드 권장
```
