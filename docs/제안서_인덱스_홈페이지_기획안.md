## 2-2. ⚠️ GitHub Pages는 권고하지 않습니다

- **저장소가 private인지 public인지 이 세션에서 확인할 수 없습니다** (GitHub 인증 없음). 사용자 확인 필요.
- 설령 private이어도 **GitHub Pages는 플랜에 따라 사이트가 public이 됩니다.** private 저장소의 Pages를 조직 구성원에게만 공개(Access control)하려면 **GitHub Enterprise Cloud**가 필요합니다. Free/Pro/Team 플랜에서 private repo의 Pages를 켜면 **URL을 아는 누구나 접근 가능**합니다.
- 즉 **고객사명 100곳 + 커리큘럼이 인터넷에 공개될 위험**이 있습니다.

# 4. 데이터 소스와 자동 갱신

## 4-1. 방식 — 파일시스템 스캔 → 인덱스 JSON 생성

**수동 관리는 100개를 넘으면 무너집니다.** 스캔 스크립트 방식을 채택합니다.

```
scripts/build_proposal_index.py
  │
  ├─ 1. projects/ 재귀 스캔 (제외 규칙 적용)
  ├─ 2. 고객사 폴더별로 HTML 그룹화
  ├─ 3. content.json 있으면 메타데이터 추출 (title/subtitle/info/tracks)
  ├─ 4. git log 로 폴더별 최초·최종 커밋일 추출
  ├─ 5. 파일명 패턴으로 문서 종류 분류
  └─→ docs/proposal-index/index.json  (약 330 항목)
      docs/proposal-index/index.html  (정적, index.json 로드)
```

**핵심 설계 결정**

| 결정 | 이유 |
|---|---|
| 산출물을 `index.json` + `index.html`로 **분리** | HTML은 한 번 만들고, 데이터만 재생성. 검색·필터는 클라이언트 사이드 JS |
| 위치는 `docs/proposal-index/` | 기존 `docs/yonsei-ax/index.html` 선례와 일관 |
| **금액 필드는 스캔하지 않음** | 2-4 등급 분리. 스캔 자체를 안 하면 유출 경로가 없음 |
| 날짜는 **git log 기준** | 폴더명 규칙이 9/100만 지켜져 신뢰 불가 |
| 상대 경로 링크 | 로컬 파일·로컬 서버 모두에서 동작 |

## 4-2. 자동 갱신 3안

| 안 | 트리거 | 장점 | 단점 | 권고 |
|---|---|---|---|---|
| **A. 수동 실행** | 사람이 `python scripts/build_proposal_index.py` | 단순. 부작용 없음 | 잊으면 낡음 | **1차** |
| **B. git hook (pre-commit)** | 커밋 시 자동 | 항상 최신 | 커밋마다 느려짐. `.claude/settings.json` hook과 충돌 가능 | 검토 |
| **C. GitHub Action** | `openwiki-update.yml`과 같은 패턴 — 스케줄 실행 후 PR 생성 | **선례 그대로 재사용**. 팀 전체에 반영 | main 기준이라 미커밋 산출물은 미반영 | **3차** |

**권고: A → C.** C는 `openwiki-update.yml`(매일 08:00 UTC, `--update` 후 PR)을 복제하면 됩니다.

## 4-3. 기존 빌드 파이프라인과의 연결

```
content.json ──build.py──▶ proposal_render.html ──▶ PDF ──▶ Google Drive
     │                            (인덱스 제외)
     └──────────────────────────────────────────┐
                                                ▼
                        build_proposal_index.py ──▶ index.json ──▶ index.html
```

- **`build.py`를 수정하지 않습니다.** 인덱스 스크립트는 읽기 전용으로 붙습니다.
- `validate-pr.yml` CI에 영향 없음 (인덱스는 `content.json` 스키마를 건드리지 않음)
- 선택: `build.py` 성공 후 인덱스 재생성을 호출하는 1줄 추가는 2차에서 검토

## 3차 — 자동 갱신 (0.5일 추정)

`.github/workflows/proposal-index-update.yml` — `openwiki-update.yml` 패턴 복제. 스케줄 실행 → `index.json` 재생성 → 변경 있으면 PR 생성.

## (선택) 4차 — 사내 서버 승격

옵션 3으로 이동. 인증 붙이고 등급 분리(견적 열람 권한)를 추가. **IT 협조·서버 확보가 전제**이므로 별도 안건.

# 7. 미결정 — 확인 부탁드립니다

| # | 질문 | 선택지 | 왜 필요한가 |
|---|---|---|---|
| **1** | **저장소가 private입니까?** | private / public / 모름 | ⚠️ **가장 중요.** public이면 인덱스 이전에 저장소 정책부터 다뤄야 합니다. GitHub Pages 사용 가능 여부도 여기서 갈립니다 |
| **2** | 상태(협상·계약·종료)를 인덱스에 표시해야 합니까? | 필요(노션 연동) / 필요(수동 관리) / 1차 제외 | 노션 연동은 별도 공수. 수동 관리는 100개에서 무너짐 |
| **3** | 견적 금액을 인덱스에 표시해야 합니까? | 표시 안 함(권고) / 권한 분리해서 표시 | 표시하면 사내 서버 + 인증이 전제됨(1차 범위 초과) |
| **4** | `content.json`에 `category`·`date` 필드를 추가할 수 있습니까? | 가능(스키마 변경) / 불가 | 추가되면 분류·날짜 정확도가 크게 오름. 단 `validate_content.py` 스키마·기존 128건 마이그레이션 필요 |
| **5** | 1차 접근 방식은? | 로컬 정적 파일 / 로컬 HTTP 서버 / 둘 다 | 정적 파일이 가장 단순. 서버는 `lead_dashboard.py` 선례 활용 |
| **6** | 인덱스를 `openwiki/`(OKF)로 통합할까요, 별도 페이지로 둘까요? | 별도 `docs/proposal-index/`(권고) / openwiki 통합 | openwiki는 문서 위키이고 인덱스는 카드 UI라 성격이 다릅니다. 다만 자동 갱신 패턴은 재사용 가치가 있습니다 |
