# /review 운영 의사결정 문서

이 문서는 사용자가 직접 관리하는 의사결정 문서입니다. Codex는 이 문서를 자동으로 덮어쓰지 않습니다. `/review` 결과가 애매하거나 사업적 판단이 필요한 경우, 아래 항목을 기준으로 사용자가 결정합니다.

## 문서 경계

| 구분 | 사용자가 관리 | Codex가 자동 작성 |
|---|---|---|
| 목적 | 리뷰 기준, 허용 수준, 사업적 우선순위 결정 | content.json 검증, 리뷰 결과 요약, 수정 제안 |
| 위치 | `docs/review_governance.md` | `scripts/validate_content.py`, `docs/review_agent_prompts.md`, 프로젝트별 리뷰 리포트 |
| 변경 방식 | 사용자가 의사결정 후 직접 요청 | `/review` 실행 시 Codex가 생성/갱신 |
| 책임 | 품질 기준과 최종 진행 여부 | 기준 적용, 오류 탐지, 영향 설명 |

## 핵심 운영 원칙

1. `FIX`는 기본적으로 빌드 전 수정한다.
2. `WARN`은 사업 맥락에 따라 유지할 수 있지만, 유지 시 영향과 이유를 남긴다.
3. `INFO`는 개선 후보로만 다루며 일정 압박이 있으면 보류할 수 있다.
4. Codex는 판단 근거와 영향을 제시하고, 최종 의사결정은 사용자가 한다.

## 의사결정 항목

### D1. WARN 3개 이상일 때 빌드 진행 허용 여부

**기본값**: 허용하지 않음. `NEEDS_FIX`로 보고 수정 후 재검토한다.

**선택지**

| 선택 | 영향 |
|---|---|
| 수정 후 빌드 | 제안서 품질은 안정되지만 납기 시간이 늘어난다. 반복 고객이나 고액 제안에 적합하다. |
| 빌드 강행 | 납기는 지키기 쉽지만 PDF 가독성, 톤, 설계 흐름 문제가 고객에게 노출될 수 있다. 내부 초안 공유에만 적합하다. |

### D2. 최신성 검토에서 외부 검색이 필요한 경우

| 외부 검색 생략 | 빠르게 진행할 수 있지만 최신 AI 도구/모델 정보가 틀릴 위험이 있다. 내부 초안이나 도구명이 일반적인 경우에 적합하다. |

### D3. 도구 일관성 오류의 수정 방식

**기본값**: `tracks[].tools`를 기준으로 `tech_stack`을 맞추고, 본문에만 등장하는 도구는 Track 도구에 추가할지 본문에서 제거할지 판단한다.

**선택지**

| 선택 | 영향 |
|---|---|
| 도구를 추가 | 고객에게 도구 범위가 넓어 보이지만 실제 교육 준비 범위도 늘어난다. |
| 본문에서 제거 | 제안 범위가 명확해지고 준비 부담이 줄지만, 실습 매력도가 낮아질 수 있다. |
| 별도 후보 도구로 표시 | 본문 완성도는 유지하면서 실제 교육 범위와 선택지를 분리할 수 있다. 단, PDF에 별도 설명이 필요하다. |

## Codex 자동작성 산출물 규칙

Codex가 자동으로 만들 수 있는 산출물은 다음으로 제한합니다.

| 산출물 | 위치 | 자동 갱신 가능 여부 | 설명 |
|---|---|---|---|
| 로컬 검증 결과 | 터미널 출력 또는 프로젝트별 리뷰 리포트 | 가능 | 스키마, 도구 일관성, 텍스트 길이 등 기계적 검증 |
| 4개 리뷰어 결과 | 프로젝트별 리뷰 리포트 | 가능 | Flow, Recency, Tone, Readability 관점별 판정 |
| 수정 제안 | 프로젝트별 리뷰 리포트 | 가능 | 사용자가 승인하기 전까지 content.json에 반영하지 않음 |
| 의사결정 기록 | 이 문서 | 자동 갱신 금지 | 사용자가 명시적으로 요청한 경우에만 수정 |

## `/review` 실행 시 사용자 확인이 필요한 경우

다음 상황에서는 Codex가 자동으로 진행하지 않고 사용자 판단을 요청합니다.

1. `FIX`가 있지만 납기상 빌드를 강행할지 결정해야 하는 경우
2. 외부 검색이 필요한 최신성 검토가 고객 제출본의 핵심 근거가 되는 경우
3. 도구를 추가하면 교육 범위나 견적이 바뀌는 경우
4. 톤 수정이 고객 포지셔닝을 바꾸는 경우
5. PDF 가독성 수정을 위해 내용을 삭제하거나 축약해야 하는 경우
